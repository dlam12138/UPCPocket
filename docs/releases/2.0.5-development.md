## 流水验证码回退

原生登录需要验证码或二次验证时，流水页显示“前往验证”。用户在学校页面手动完成验证，应用截获当前主框架的校园卡登录结果，经本人核验与账号代次/业务 epoch 检查后恢复原生页面。只查询当前日期筛选的第一页；“全部日期”保持原语义，“加载全部”仍由用户再次点击。

保留现有插件/宿主装配、受控凭据、原生登录和本人只读接口。普通登录页的二维码/SMS 选项不会单凭静态文字阻止有效密码表单；明确验证码和活动挑战继续停止原生密码提交。精确 `/cas/login` 支持学校 iframe 表单 POST，iframe 不能消费登录结果。重复回调只处理一次，取消、清理及账号变化拒绝迟到结果。

账号失效先停止活动 WebView，再清理学校 Cookie；停止失败保留清理句柄，后续重试不能绕过屏障。只补已知校园卡 Cookie 主机与路径，不宣称枚举所有浏览器存储。WebView 禁用 DOM Storage、数据库、文件/内容访问、混合内容和第三方 Cookie，不注入 JS bridge、不自动填密码、不保存网页登录状态。

## 边界

Android `shouldOverrideUrlLoading` 不覆盖应用自身 `loadUrl` 或所有 POST；初始入口与资源回调另行检查。`shouldInterceptRequest` 在后台线程且只报告子资源重定向的初始 URL；`onPageStarted` 不保证在网络发送前触发。因此当前限制不构成对子资源后续重定向的严格逐跳事前阻断，也未实现携带学校 Cookie 的资源代理。实际验证码资源依赖和学校回调形状仍须在真实挑战发生时验证；合成成功不等于校园验证码实测通过。

真实学校验证码与票据兑换、网络/TLS/HTTP 失败、renderer 崩溃、真机、完整字体/旋转/尺寸矩阵及全部三个组件未验证。

## 2026-11-13 登录回退修复

用户反馈反复点击登录后才出现网页验证。本轮确认并修复了两个源码缺口，但没有使用校园账号复现该反馈，不能据此断言已经穷尽实际问题的全部根因。

- 原生校园卡认证原先对所有 HTTP 400 以上响应直接报协议错误，丢弃 CAS 401/403 中仍然有效的登录/验证码表单。现在仅对精确 HTTPS `cas.upc.edu.cn/cas/login` 的 401/403 且可识别的密码或挑战表单立即返回交互要求；GET 阶段不提交密码，POST 后遇到这类响应最多保留本次一次提交，不自动重试。
- 未识别 HTML、仅含帮助/登录选项文字的页面、其它主机/路径、429、5xx、TLS 和网络错误不伪装为验证码。共享 transport、域名单、TLS 和已验证的 WebView 生命周期未改变。
- 有交互适配时，流水页初次进入即显示稳定的“网页登录”，显式挑战改为“前往验证”。重试期间保持已知挑战状态，成功或账号变化才清除；忙碌、无账号、清理中或已打开验证页时禁用。不开自动弹窗，不为试出验证码重复提交密码。

### iframe 设备实测与处理边界

独立 researcher 与 planner 核对平台边界后，保留子资源票据拒绝策略。[WebResourceRequest 官方定义](https://developer.android.com/reference/android/webkit/WebResourceRequest#isForMainFrame())明确 `isForMainFrame=false` 同时包含 iframe 与普通子资源；请求头 API 也不保证提供文档目标类型。不能凭正确 URL、`Accept`、之前的 POST 或回调先后次序，就将图片/fetch 视为登录完成。

据此追加用户主动的“继续”路径：完成学校验证但未自动返回时，重新打开固定登录入口，以新的顶层登录结果完成核验。它不消费先前被拦截的子资源票据，也不将点击动作当作登录成功。真实学校能否利用已有会话重新签发顶层票据，仍需本人真实环境验证；没有有效会话时继续显示学校登录页，不自动循环或补交密码。
