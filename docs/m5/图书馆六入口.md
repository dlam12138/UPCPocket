HTTP 200 当成预约成功。原始 HAR 仍是只读证据，未修改、未上传、未删除。

## 2. 统一入口与平台隔离

- 首页“常用服务”只保留一个“图书馆”入口，路由 `library.home`；进入后按唐岛湾/古镇口/求是分组
  显示六个平台。底部仍是三 tab，不增加新的顶级目录。
- 既有 `library.seat`（libseat 页）和 `library.login` 路由保留；nspace 路由保留；新增：
  - `library.chaoxing.seat` / `library.chaoxing.seatengine`
  - `library.chaoxing.reserve` / `library.chaoxing.reserve.qiushi`
  - `library.chaoxing.login`
- `LibraryCapabilities.seat`、`nspace`、`chaoxing` 是三个独立能力：
  - `LibraryService` 持有 libseat seat token 和可选加密副本；
  - `NspaceService` 使用独立 nspace business token、`/spa` 模型和内存会话；
  - `ChaoxingService` 只持有本次受限 WebView 登录得到的 Chaoxing Cookie（内存），
    不与 libseat/nspace token 混用。
- 统一账号换号/删号时，宿主调用 libseat、nspace、Chaoxing 三个
  `signOutForAccountChange()`；Chaoxing 同时清理应用 WebView 的固定 host/path Cookie，
  任一清理失败仍按既有账号失效器阻止个人会话。
- nspace 登录仍走 `core:upc-auth` 的受控凭据与正常 CAS；业务代码不读取密码。
- Chaoxing 四入口在原官方页回退之外，已有原生只读页；原生页不会替用户提交预约、取消、
  签到、团队或成员变更。

## 3. nspace 协议边界与多人状态

公开 nspace 前端配置（`config.js`）给出：

```text
BASEURL    = https://libspace.upc.edu.cn/spa
VUESERVICE = https://libspace.upc.edu.cn/nspace/#/login
CASSSERVICE= https://libspace.upc.edu.cn/remote
```

认证按以下顺序实现，全部固定 HTTPS 主机/路径：

1. `GET https://libspace.upc.edu.cn/remote/static/sso/login?redirectUrl=<nspace login>`；
   实测返回 **302** 到 `https://cas.upc.edu.cn/cas/login?service=<libspace casLogin>`。
2. 正常 CAS 表单只提交一次密码；回调路径仍是
   `/remote/static/casAuth/getServiceByVerifyTicket/casLogin`。
3. 从回调后续 URL 的 query 或 fragment 取得 nspace **app token**；只接受 libspace 固定
   `/nspace` 路径，不跟随外部主机。
4. `GET /spa/static/public/api/remoteCasLogin?token=<app_token>`，严格检查
   `status/code`，取 `data.token` 与 `data.userInfo`。
5. 用服务端 `userInfo.username` 经 `SchoolAccountIdentityVerifier` 与当前账号比较；不一致不发布。

只读接口：`getVenueList`、`getRoomTypeList`、`getOpenDateList`、`getRoomList`（JSON POST，
`currentPage/pageSize/selectDate`）。`getRoomList` 保留学校分页，未把 401 或空 `pageList`
当作“无房间”。

官方预约深链：房间卡片只使用学校公开前端自己的
`#/detail?id=<roomId>&selectDate=<yyyy-MM-dd>` 路由，不带 token、uid、enc、code 或其他
用户上下文；登录、选择时段、必填项与真正提交都在学校官方页面完成。

**官方 CAS 交互回退**：自动 CAS 遇到验证码/二次验证时，页面提供
“网页登录（验证码/二次验证）”，加载固定 nspace 入口到学校 WebView；用户在学校页面正常
完成登录，应用不预填/不读取密码。WebView 只捕获 libspace `/nspace` 页面 query/fragment 中的
临时 app token，交给 `loginWithWebToken`，再走 `remoteCasLogin`、本人核验、账号代次/epoch/
revision 发布门闩；换号/退出后的迟到回调不发布。token 不持久化，也不与 libseat token 混用。
WebView 只允许 `*.upc.edu.cn` HTTPS，证书错误直接停止。

**原生预约表单**：`getRoomDtoByRoomIdAndDate`、`getAllUseType`、`getRequiredOption`、
`saveReservation` 的模型/解析/时段和必填规则已接入单人表单，并有一次最终“真实预约”
确认。只对非多人、非选座、非附件、表单类型可支持且时段合法的房间显示提交；新预约提交
`begin/end/onDate/roomId/useType/participants/filePath/source/seatNo/teamId` 与
`theme/phone/outline/extraField`。没有真实点击最终确认提交，`stopBook`/团队/签到仍未实现。

### 3.1 公开前端多人/团队协议（只读复核）

公开 A123 预约表单 chunk 和 API 封装给出：

- `GET /spa/static/api/book/searchUser?searchKey=<key>` 返回可选用户，前端读取
  `username` 与 `fullName`；`GET /spa/static/api/book/verifyUsername?username=<username>`
  返回 `"fullName/username"` 字符串。
- 最终 `saveReservation` 的 `participants` 是**被邀请人 username 的逗号连接**：
  `this.userList.join(",")`；主预约人由服务端按当前 token 识别，不重复写入 `participants`。
- `teamId` 默认 `0`，编辑已有订单时从服务端 `order.teamId` 回填；团队模式使用
  `queryUserTeamList`、`queryTeamTimeLimit`、`joinTeamByKey/{key}`、`createTeam`、
  `addParticipant`。单人邀请模式不发团队请求。
- 房间人数规则来自 `minUser/maxUser`；A123 为 3–6 人，`bookPolicy.minTime=60`、
  `maxTime=120`。前端在团队人数超过 `maxUser` 时提示“解散重新组队”，不足 `minUser`
  时提示组队；这些提示不是服务端成功。
- 只读查询本人 `queryUserTeamList`（空 body）返回 HTTP 200、`code=200`、`pageList` 为空、
  `totalCount=0`，即当前账号没有可复用团队。没有调用 `searchUser` 搜索真实姓名、没有
  加入/创建团队、没有调用 `addParticipant`/`saveReservation`。

**本轮结论**：协议形状足以说明“普通邀请 + `teamId=0` + participants 逗号连接”是公开
前端的路径，但本轮没有获得可安全验证的受邀成员，也没有授权执行真实邀请/团队/预约；
因此应用仍只对 `minUser=1` 的房间原生提交，A123 等多人房间明确引导官方页面，**不伪造
参与人、团队或 `teamId`**。这不是把多人流程宣称为已完成。

**已实现的写操作**：`cancelBook/{id}` 只按公开前端确认的 `GET` 路径调用；仅对学校返回
`status=0` 的记录显示取消按钮，并且必须经过确认对话框。取消成功后重新读取本人列表，仍以
服务端状态为准。没有用真实记录执行取消；`stopBook`（提前结束使用）未接入。

## 4. Chaoxing 原生只读接入

### 4.1 认证契约与真实边界

现有 Chaoxing 会话来自此前的微信 `wfw` 上下文，不是从统一学校账号自动建立。真实检查：

- `https://office.chaoxing.com/front/third/apps/seat/index?fidEnc=<fid>&mappId=4197453`
  在**已登录**会话直接进入座位首页；未登录会到 `passport2.chaoxing.com/login`。
- `passport2` 登录页要求 **手机号/超星号 + 学习通密码**，不是学校 CAS 表单。统一学校账号的
  密码没有在 `passport2` 上验证过；应用不能把学校密码自动提交给 Chaoxing，也不能把
  微信 `wfw` 一次性入口当作长期登录契约。
- 因此产品路径是：应用内**受限官方 WebView** 加载稳定座位入口，由用户在学校/Chaoxing
  官方页面正常登录；应用不预填、不读取、不保存密码，只读取应用 WebView 的 Chaoxing
  Cookie，并用服务端 `userLoginInfo.sno` 与当前统一账号比较。真实 App 内用学校凭据完成
  Chaoxing 登录仍未验收；这是本轮最重要的认证阻塞，不是接口字段问题。
- 身份/账号门闩：登录回调在锁外请求，发布前检查 `SchoolAccountGate`、账号代次、epoch、
  revision；旧回调、换号、删号、退出后的结果不发布。Cookie 只存在 `ChaoxingService` 内存，
  不写 DataStore/账号库/日志；换号/退出/会话失效时清理应用 WebView 的固定 host/path
  Cookie。系统浏览器、Edge、其他 profile 的 Cookie 不读取、不复用。
- 固定 host/path allowlist；主框架只允许 `office.chaoxing.com`、`reserve.chaoxing.com`、
  `passport2.chaoxing.com` 等明确登录 host，HTTPS，证书错误直接停止，不绕过 TLS。

### 4.3 reservepc：解析/UI 已实现，但当前稳定 URL 缺租户上下文

reservepc 列表接口要求 `reserveIdEnc`（服务端页面渲染的租户上下文，不是用户票据）：

1. 先以同一 Cookie 打开 `https://reserve.chaoxing.com/front/web/apps/reservepc/index`
   官方页面，解析 `reserveIdEnc`；
2. 再 `POST /data/apps/reserve/item/list/time` form
   `sw&reserveId&resvAppId&startTime&endTime&reserveIdEnc&fidEnc`；
3. 解析 `data.reserveItemList` 的 `id/name/minUserNum/maxUserNum/timeUnit/reserveIntervalList/
   details`。

真实请求的稳定 URL（只含 `reserveId/resvAppId/fidEnc/mappId`）当前返回 **302** 到
`/front/third/apps/reserve/item/index`，再 **303** 到
`/front/apps/reserve/error/code/500?msg=未查询到您所访问的应用`。这不是会话失效，也不是
空列表，而是缺少学校业务目录生成的 `reserveIdEnc` 上下文；HAR 原始页面能读 8/23 个房间，
因为它带有该上下文，但其中的一次性 `enc/code/state/wfwEnc` 不能硬编码/长期保存。

因此原生页在无上下文时显示：

> 该研讨间入口需要学校业务目录生成的租户上下文；当前只提供官方页回退，未把 302 当作空列表。

并保留官方入口按钮。解析器/类型/租户隔离/错误码均有测试；没有伪造 8/23 个房间，也没有
执行 reservepc 预约、取消、团队或附件操作。

## 6. 需要用户的最小协助 / 精确边界

1. **Chaoxing 真实 App 内登录**：需要用户用手机号/超星号 + 学习通密码在应用内官方 WebView
   登录一次；或提供学校目录中当前有效的微信 `wfw` 入口。不能把统一学校账号密码自动提交到
   `passport2`，也不复制旧 HAR 的一次性 `enc/code/state/wfwEnc/uid`。
2. **reservepc 租户上下文**：需要学校图书馆/业务目录当前生成的研讨间入口（或学校管理员确认
   稳定入口的上下文参数）。当前稳定 URL 302 到“未查询到应用”，应用已明确显示该阻塞，
   不伪造房间列表。
3. **nspace 多人**：A123 等房间需要 3–6 人；普通邀请虽在公开前端表现为
   `participants=<username,username>&teamId=0`，但没有可安全验证的受邀成员/授权，
   应用仍引导官方组队。需要真实成员和明确授权后才能做提交级验证。
4. **写操作**：六入口均没有点击任何真实最终预约/取消/签到/团队/成员变更；需要另行明确
   授权并由用户自行确认。

没有完成的部分，本轮不把 #4/#6 的浏览器列表或 #3/#5 的座位图写成“六平台原生全通”。
