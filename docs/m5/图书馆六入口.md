## 2. 统一入口与平台隔离

- 首页“常用服务”只保留一个“图书馆”入口，路由 `library.home`；进入后按唐岛湾/古镇口/求是分组
  显示六个平台。底部仍是三 tab，不增加新的顶级目录。
- 既有 `library.seat`（libseat 页）和 `library.login` 路由保留；新增 `library.nspace`。
- `LibraryCapabilities.seat` 与 `LibraryCapabilities.nspace` 是两个独立能力：
  - `LibraryService` / `LibrarySeatRepository` 继续持有 libseat seat token 和可选加密副本；
  - `NspaceService` / `NspaceRepository` 使用独立的 nspace business token、`/spa` 模型和内存会话；
  - 两者不共享 token、解析器或 Cookie 假设。nspace token 不持久化，退出/换号即清。
- 统一账号换号/删号时，宿主既调用 libseat `signOutForAccountChange()`，也调用
  `NspaceService.signOutForAccountChange()`；任一失败继续按既有账号失效器阻止个人会话。
- nspace 登录仍走 `core:upc-auth` 的受控凭据与正常 CAS；业务代码不读取密码、不依赖
  `core:account`、不把 nspace token 当作 seat token。
- Chaoxing 四入口是**官方网页回退**，不是原生能力：应用只校验固定 `office.chaoxing.com` /
  `reserve.chaoxing.com` HTTPS 主机后交给系统浏览器；不读取、保存或代理 Chaoxing Cookie。

## 3. 新增 nspace 协议边界

公开 nspace 前端配置（`config.js`）给出：

```text
BASEURL    = https://libspace.upc.edu.cn/spa
VUESERVICE = https://libspace.upc.edu.cn/nspace/#/login
CASSSERVICE= https://libspace.upc.edu.cn/remote
```

新增认证按以下顺序实现，全部固定 HTTPS 主机/路径：

1. `GET https://libspace.upc.edu.cn/remote/static/sso/login?redirectUrl=<nspace login>`；
   实测返回 **302** 到 `https://cas.upc.edu.cn/cas/login?service=<libspace casLogin>`。
2. 正常 CAS 表单只提交一次密码；回调路径仍是
   `/remote/static/casAuth/getServiceByVerifyTicket/casLogin`。
3. 从回调后续 URL 的 query 或 fragment 取得 nspace **app token**；只接受 libspace 固定
   `/nspace` 路径，不跟随外部主机。
4. `GET /spa/static/public/api/remoteCasLogin?token=<app_token>`，严格检查
   `status/code`，取 `data.token` 与 `data.userInfo`。
5. 用服务端 `userInfo.username` 经 `SchoolAccountIdentityVerifier` 与当前账号比较；不一致不发布。

只读接口：`getVenueList`、`getRoomTypeList`、`getOpenDateList`、`getRoomList`（JSON POST，
`currentPage/pageSize/selectDate`）。`getRoomList` 保留学校分页（本轮实测 11 个房间，分页），
未把分页拍平，也没有把 401 或空 `pageList` 当作“无房间”。

官方预约深链：房间卡片只使用学校公开前端自己的
`#/detail?id=<roomId>&selectDate=<yyyy-MM-dd>` 路由，不带 token、uid、enc、code 或其他
用户上下文；登录、选择时段、必填项与真正提交都在学校官方页面完成。

**官方 CAS 交互回退**：自动 CAS 遇到验证码/二次验证时，页面提供
“网页登录（验证码/二次验证）”，加载固定 nspace 入口到学校 WebView；用户在学校页面正常
完成登录，应用不预填/不读取密码。WebView 只捕获 libspace `/nspace` 页面 query/fragment 中的
临时 app token，交给 `loginWithWebToken`，再走 `remoteCasLogin`、本人核验、账号代次/epoch/
revision 发布门闩；换号/退出后的迟到回调不发布。token 不持久化，也不与 libseat token 混用。
WebView 只允许 `*.upc.edu.cn` HTTPS，证书错误直接停止。

**原生预约表单**：`getRoomDtoByRoomIdAndDate`、`getAllUseType`、`getRequiredOption`、
`saveReservation` 的模型/解析/时段和必填规则已接入单人表单，并有一次最终“真实预约”
确认。只对非多人、非选座、非附件、表单类型可支持且时段合法的房间显示提交；新预约提交
`begin/end/onDate/roomId/useType/participants/filePath/source/seatNo/teamId` 与
`theme/phone/outline/extraField`。没有真实点击最终确认提交，`stopBook`/团队/签到仍未实现。

### 3.1 公开前端多人/团队协议（2026-11-04 只读复核）

公开 `950.bdb0eae0.js`（A123 预约表单 chunk）和 `app.a47218f3.js`（API 封装）给出：

- `GET /spa/static/api/book/searchUser?searchKey=<key>` 返回可选用户，前端读取
  `username` 与 `fullName`；`GET /spa/static/api/book/verifyUsername?username=<username>`
  返回 `"fullName/username"` 字符串。
- 最终 `saveReservation` 的 `participants` 是**被邀请人 username 的逗号连接**：
  `this.userList.join(",")`，`userList` 来自 `userTag.map(t => t.value)`；主预约人由服务端
  按当前 token 识别，不重复写入 `participants`。
- `teamId` 默认 `0`，编辑已有订单时从服务端 `order.teamId` 回填；团队模式使用
  `queryUserTeamList`（当前用户的团队与 `userInfoList[].status`）、`queryTeamTimeLimit`、
  `joinTeamByKey/{key}`、`createTeam`、`addParticipant`。单人邀请模式不发团队请求。
- 房间人数规则来自 `minUser/maxUser`；A123 为 3–6 人，`bookPolicy.minTime=60`、
  `maxTime=120`。前端在团队人数超过 `maxUser` 时提示“解散重新组队”，不足 `minUser`
  时提示组队；这些提示不是服务端成功。
- 本轮只读取协议、房间和表单，没有调用 `searchUser` 搜索真实姓名、没有加入/创建团队、
  没有调用 `addParticipant`/`saveReservation`。应用仍只对 `minUser=1` 的房间原生提交；
  A123 等多人群房间继续引导官方页面，不伪造参与人、团队或 `teamId`。

**已实现的写操作**：`cancelBook/{id}` 只按公开前端确认的 `GET` 路径调用；仅对学校返回
`status=0` 的记录显示取消按钮，并且必须经过确认对话框。取消成功后重新读取本人列表，仍以
服务端状态为准。没有用真实记录执行取消；`stopBook`（提前结束使用）未接入。

## 5. 模拟器凭据测试与 CAS 验证码（历史）

2026-11-04 在测试 APK 的私有目录中通过 stdin 写入临时 JSON，仅由测试进程读取。没有把
凭据写入源码、文档、日志、命令行参数、截图或 Git；测试结束后删除临时文件、加密账号和
账号状态目录，用户来源文件和既有 Edge 未改动。这是**模拟器路径**；独立 Chrome 的后续
检查见 5.2。

实际结果：

1. nspace 固定入口 `/remote/static/sso/login` 返回 302 到 CAS（不是 `/nspace/remote`；
   后者 404，不是产品入口）。
2. CAS 登录页可加载；提交一次后服务器返回 **401 + 登录/验证码页面**。此前 CAS 把 401
   直接映射成 `ACCESS_DENIED`，会误报为“拒绝”；本轮修复为解析 401/403 页面：
   有验证码/密码表单或二次验证时返回 `INTERACTION_REQUIRED`，保留交互 URL；没有可交互
   表单时才返回拒绝。
3. 按“不绕过、不重复失败密码”的要求立即停止，没有继续多次提交，也没有把 401 当作
   密码错误或登录成功。
4. 这是 **CAS 要求用户交互**，不是“无凭据”，也不是“认证成功”。
