## 1. 目标与决策

在 UPC Pocket Lightly v0.2.7 的基础上增加统一学校账号设置，允许用户主动将账号密码加密保存在本机。各业务按需使用统一认证能力建立独立会话；优先完成校园卡余额的账号强关联和 UPC 课表查询、展示、缓存。

本方案记录本轮用户确定的新方向；原始 [总体计划 v0.1](../UPC-Pocket-总体计划-v0.1.md) 保留原文，不用历史暂停状态覆盖本轮文档工作。当前已发布能力仍以 [README](../README.md) 为准。

| 决策 | 工程含义 |
| --- | --- |
| 模块化与插件化优先 | 先拆分现有 Gradle 模块、建立插件契约与依赖边界，再接入新账号和课表能力 |
| 页面安排与设计最后统一处理 | 功能阶段沿用现有风格及导航；新增页面先提供可用交互，全应用排布和视觉优化留到 M5 |
| 新增本地加密保存账号密码 | 建立独立凭据存储和统一认证入口，保存与在线认证分开反馈 |
| 校园卡余额与统一账号强关联 | 查询目标只来自当前绑定的本人学号，页面与组件不再各自保存独立查询账号 |
| 优先恢复课表 | 第一阶段提供学期选择、周课表、今日课程和已查询课表的离线查看 |
| 石光、e站通后置 | 用户反馈已有方便的官方移动端入口；原生聚合不作为首轮验收条件 |
| 已有功能继续可用 | 保留电量、空教室、图书馆、专注与现有两个 RemoteViews 组件，不做全量重写 |
| 复用 UPC-MCP 的业务研究 | 移植协议、解析、错误语义与有价值的测试场景；不嵌入 Python、MCP 服务或桌面配置设施 |

用户反馈已与学校取得联系，并提出未来成为官方移动客户端的可能性。这属于合作方向，尚不能据此记录为已获官方身份、统一认证接入资格或全量接口授权。后续确认的接口范围、学校对接方式和品牌许可另行记录；本轮文档不代替这些事实。

## 4. 账号设置与操作语义

首版只维护一个当前学校账号，不建设多账号切换列表。功能阶段先将设置入口放在“更多 → 学校账号”，沿用现有组件；最终位置与布局由 M5 统一设计。

### 4.1 保存与检查

- 提供学校账号、密码、确认密码，以及明确的“加密保存到本机”说明。密码默认隐藏，仅保留在当前输入内存中，不进入 `rememberSaveable`、SavedStateHandle、日志、剪贴板或自动填充的持久副本。
- 保存后清空密码输入框，不回显已保存密码。后续修改密码需要重新输入并确认。
- 保存成功只显示“已保存，尚未验证”；不显示“已登录全部系统”。格式检查也不代表学校认证通过。
- “检查课表连接”等操作单独发起对应业务认证。不能把所有系统的成功与失败合成一个笼统的绿色登录状态。
- 普通输入修改不发网络请求；保存动作不同时查询所有业务。业务按用户进入或主动刷新时连接。
- 一次保存只落一个完整凭据版本。加密或磁盘提交失败时保留原有可用版本，显示固定错误文案，不携带底层异常或输入内容。

### 4.2 修改、退出与删除

| 操作 | 行为 |
| --- | --- |
| 同账号更新密码 | 递增认证代次，清理旧认证及业务会话；同账号缓存可保留为历史值，等待重新验证 |
| 更换账号 | 先使旧账号失效，再清除旧个人会话、缓存及组件内容，最后启用新账号；不得沿用旧账号业务身份 |
| 退出某业务 | 清除该业务会话；在用户再次进入或主动重连前，不因后台恢复立即将其重新登录 |
| 删除学校账号 | 清除账密、关联业务会话与个人缓存、旧余额输入和组件内容；下次查询提示设置账号 |
| 仅清除某业务缓存 | 删除该业务快照，阻止迟到结果重新写回；保留账号与其他业务状态 |

换号和删号均不删除专注历史、主题配置、公开教室数据或寝室配置。寝室不是学校账号自动推导出的属性，电量沿用用户明确设置的房间。

## 5. 模块边界与认证流程

以下为拟新增职责名称，不代表仓库已有同名类；实现时可按现有包结构调整。

```text
账号设置 / 业务页面 / ViewModel
             ↓
SchoolAccountRepository（当前账号、代次、状态）
        ↙                       ↘
SchoolCredentialStore       SchoolAuthCoordinator
Keystore 加密账密          按需认证、单业务锁、交互升级
                                  ↓
                    课表 / 图书馆等业务 SessionProvider
                                  ↓
                         业务 Repository 与本地缓存

余额 Repository → 读取当前绑定学号 → 学校余额接口
电量与公开教室 → 沿用各自查询链路
```

### 5.1 凭据、身份、会话分开

- `SchoolCredentialStore` 仅供认证模块读取明文凭据；对 UI、组件、Worker 和普通业务 Repository 不暴露密码。
- `SchoolAccountRepository` 对外仅提供脱敏显示信息、应用内部 accountId、认证代次和凭据可用状态。业务确需本人学号时使用受控读取接口。
- 首版以用户明确填写的本人学号绑定余额。课表若支持不同形式的 CAS 登录名，应另行区分 loginName 与 studentId；未能取得或确认本人学号时禁用余额，不猜测、不直接把任意登录别名当成学号。
- 同一份账密可用于多个业务认证，但各业务 Cookie/token、退出状态、错误与恢复锁独立。图书馆 token 不能代替课表 Cookie。
- 本地保存的账号不自动等于业务返回的身份。业务响应若提供可核对的本人标识，必须核对；来源不提供时标记“身份未独立核验”，不声称完成了强身份验证。

### 5.2 认证与恢复

1. 业务被主动打开或刷新时，读取当前账号快照与认证代次。
2. 优先使用该账号已有有效业务会话；同业务并发请求合并登录，避免重复提交密码。
3. 仅缺会话或遇到已识别的认证失效时，按该系统的正常学校认证流程建立业务会话。
4. 一次业务请求最多自动恢复并重试一次；认证失败停止，错误密码、网络故障和业务拒绝分别反馈，不循环重登。
5. 验证码、二次验证或未适配的认证步骤进入“需交互登录”，打开学校正常登录路径，不尝试绕过。
6. 业务身份与代次仍一致，才接收结果、保存会话和更新缓存。

密码只用于核实后的学校 CAS HTTPS 认证端点。严格验证证书与重定向目标，不在跳转时向其他主机转发密码或认证头。Cookie 保留原有 domain、path、secure、到期等约束，不跨业务随意拼接。

共享账密的本地认证便利不等于已取得官方单点登录资格。认证层保留可替换的 Provider 边界：学校未来提供正式移动端认证时替换认证适配，业务与 UI 不直接依赖密码。

### 5.3 并发、换号与进程恢复

- 所有个人请求捕获 `(accountId, credentialGeneration, businessGeneration)`。响应发布、落盘、组件刷新前再次校验；取消协程不能代替这个校验。
- 换号或删号通过账号级串行协调执行；代次先持久化为不可用/切换中，再清理，清理完成后才发布新状态。
- 删除或切换中途进程退出，重启必须先完成清理再允许个人查询，不能把半完成状态当成正常账号。
- 业务会话保存 accountId 与认证代次；个人缓存至少保存 accountId 与数据范围。缓存可否展示与会话可否复用分开判断。
- 统一处理现有 WebView 的学校 Cookie：换号或删除时，在允许新登录前清理学校登录上下文并等待完成，防止自动带回旧身份；清理策略不得无故退出无关外部站点。
- 已排队的余额 Worker 不携带密码或完整凭据。执行时读取当前绑定与代次，旧任务失效后结束，不刷新出已删除账号的内容。

## 6. 校园卡余额强关联

强关联是应用内的查询目标约束，不改变学校余额接口的鉴权事实。该接口仍按学号查询，不接收密码，不因绑定账号而变成 CAS 认证接口；现有 HTTP 传输边界也不因此消失。

### 6.1 新行为

- 余额页展示当前账号的脱敏学号，提供“前往账号设置”，取消独立可编辑学号查询框。
- 页面刷新与组件刷新只能使用账号 Repository 给出的本人学号，不接受来自路由、组件参数或旧快照的任意查询目标。
- 无绑定账号时不发请求，显示“请先设置学校账号”。已保存但认证未验证时如实标注；余额接口无需 CAS，其成功不能反证密码正确。
- 同账号查询失败可保留最后成功值与绝对时间，并标明为历史缓存。新账号不能继承旧账号余额，即使新账号还没查成功也不能临时显示旧值。
- 组件目标由当前账号确定，不再依赖“旧目标查询成功后才切换”的策略。保存新账号即撤下旧内容，等待新账号首次查询成功。
- 保留校园卡余额与过渡余额的区别，不擅自改称现金、欠费或可消费合计。

### 6.2 旧版迁移

| 原有数据 | 迁移规则 |
| --- | --- |
| `cardStudentId` 输入草稿 | 仅可作为账号设置的待确认提示，不自动创建账号、不推断密码或本人身份 |
| `card-balance-v1.json` | 未绑定账号前不展示；用户绑定同一学号后可迁为带 accountId 的历史缓存，保留原查询时间 |
| 不同学号的旧余额 | 清除，不迁移到新账号；解析损坏时也不能回退显示未知归属的数值 |
| 旧组件实例 | 保留实例；更新为“待绑定账号”或当前账号状态，不要求卸载重装 |

账号来源切换与缓存格式升级必须有幂等迁移标记。完成后不再读取旧学号作为查询来源，删除遗留明文学号草稿；迁移失败不得自动查询。专注数据库与电量快照保持可用。

## 7. 课表查询与展示

### 7.1 来源与复用边界

来源参考为 [UPC-MCP](https://github.com/dlam12138/UPC-MCP) 的本机源码审阅；本轮未联网验证学校接口，也未执行真实账号认证。后续移植须固定参考提交并记录许可证与来源，不能只引用浮动分支。

参考模块：`timetable_protocol.py`、`timetable_service.py`、`timetable_tools.py`、`auto_auth/providers/timetable.py` 及对应测试。保留必要 MIT 版权声明，不复制桌面状态目录、凭据、个人业务响应或浏览器 profile。

源码当前使用的 UPC 校园 App 路径：

- 入口：`https://app.upc.edu.cn/site/weekschedule/index`
- 学期与当前周：`GET /timetable/wap/default/get-index`
- 周课表：`POST /timetable/wap/default/get-datatmp`，`type=2`，其余参数按固定提交核对

这些是参考实现中的协议事实，不是校方公开 API 承诺；正式实现时补充到 [官方入口资料](upc/官方入口.md) 和 [开发目录](upc/official-entrypoints.json)，标清源码依据、实际验证范围和认证要求。

### 7.2 首版界面与缓存

- 功能阶段先提供“更多 → 课表”原生页面，含周课表与今日课程；首页今日课程摘要及最终入口位置留到 M5，不改动底部导航结构。
- 学期选择、教学周切换、周网格、今日课程、课程详情和主动刷新。详情包含来源有提供的课程名、教师、地点、日期、节次与周次。
- 首次只查当前所需教学周；切周按需加载。不提供默认整学期预取或周期轮询。
- MCP 日期范围查询上限为 14 天/3 个教学周；周课表无需依赖整学期工具。后续需要日历范围查询时保持显式范围与完整性语义。
- 按 accountId、学年、学期、教学周缓存；保留获取时间和源数据范围。离线只能展示已成功缓存的周，未缓存周提示不可用。
- 已完整查询且确实为空，才能显示“本周无课程”；认证失败、解析失败、未查询、离线无缓存均不能显示成空课表。
- 教师、地点或钟点缺失时显示“未提供”，不推测教室、校区或学校作息。不强行给没有来源的节次填入时刻。

### 7.3 日期与节次语义

- 使用 `Asia/Shanghai` 计算今日日期；区分自然周、学校教学周和界面列顺序。
- 参考实现声明教学周从周日起算，同时对外星期使用 ISO 编号（周一=1、周日=7）。UI 可周一在前，但不得据此重算错误的教学周归属。
- 课程日期以接口显式日期与星期一致性为依据，不能仅按某个假定开学日外推。校验失败保留错误状态，不静默移动课程。
- 保留实际周次集合、非连续节次、多条同日课程和重叠课程，不只用起止范围近似；单/双周依据源数据，不靠展示文案猜测。
- 字段矛盾、节次越界或协议变化应拒绝覆盖成功缓存；错误页不输出原始业务响应。

### 7.4 Room 演进

五张旧课表表不直接等于新 UPC 数据模型。先对照源字段与身份隔离要求设计新领域模型，再决定新增账号归属表/课表表或复用结构。

涉及 schema 变化必须提升数据库版本、导出新 schema、提供从现有 version 1 的显式迁移。不使用 destructiveMigration，不清空专注历史。旧课表数据不得自动作为当前账号的 UPC 课表；即使沿用旧表，也必须能证明账户归属后才允许展示。

## 8. 数据保护与故障状态

| 数据 | 处理要求 |
| --- | --- |
| 账号密码 | 应用私有文件中只存 AES-GCM 密文；独立 Keystore key alias 与版本，不与业务会话混存 |
| 业务 Cookie/token | 独立业务存储并加密，包含账号归属；恢复失败只影响相关业务 |
| 余额与课表缓存 | 带账号归属及查询时间，位于应用私有目录并排除备份；不把“账密加密”描述为所有缓存均已加密 |
| 页面输入 | 密码仅在当前页面内存短暂存在；离页与保存后清理，不预填已存密码 |
| 日志与崩溃信息 | 不记录密码、Cookie/token、请求正文、带票据 URL、原始个人响应；使用固定错误码和脱敏摘要 |
| 测试与发布材料 | 使用虚构数据与替身认证服务；真实账号不进入 fixture、截图、文档和提交 |

凭据存储复用现有加密思路，但与 `SchoolSessionStore` 分离：新增凭据 key alias、版本化密文格式、每次加密新 IV 与完整性校验。用同步可靠提交确认“保存成功”，不将异步落盘排队等同持久成功。

密钥丢失、密文损坏或格式不支持时，不崩溃、不降级明文；账号转为“需重新配置”，失效关联会话并隐藏不能确认归属的个人数据。不得误清专注记录或公开数据。删除完成后账密、关联会话、缓存与组件都不可再恢复；该动作不代表撤销校方服务器上的所有会话。

业务状态至少区分：未配置账号、已保存未验证、连接中、已连接、需交互登录、密码/认证失败、网络不可用、协议变化。缓存状态与连接状态分别表达，旧值必须保留上次成功时间。

### 9.1 自动化测试重点

1. 凭据密文落盘、错误密文/密钥失效、保存失败保留旧版本、删除后不可读。测试替身只能验证业务行为，真实 Keystore 另在设备验证。
2. 账号 A 查询中切换 B、同账号更新密码、删除后迟到响应、进程在清理中退出；页面、持久缓存与组件均不能出现旧账号内容。
