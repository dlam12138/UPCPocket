## 1. 先修本次复核确认的问题

### 课表学期日期与用户设置

现有 `SchoolScheduleSyncScreen.plan()` 对所有选中学期都传入 `ui.page.currentWeek`；`SchoolScheduleSync.build()` 据此用今天反推第 1 周，导致历史学期可能使用本学期日期。

- 只有确认所选学期就是学校当前学期，才允许将当前教学周作为日期推算依据；推算结果明确标为推算。
- 优先查真实响应是否有对应学期的开学日。第三方实现使用了 `params.startday`，这是待核验线索，不是已证明每个学期均返回该字段。
- 历史或日期未知的学期使用已保存的用户设置，或在提交前让用户确认第 1 周日期；不能自动编造日期后让用户事后修正。
- `saveSchoolTerm()` 当前会重写 `startDate/endDate/weekStartOnSunday/isCurrent`。明确区分“更新学校课程”和“修改用户学期设置”：保留已确认日期、周起始设置和当前学期状态；只在明确需要且用户知情时改变。
- 更改第 1 周日期后，所有课程日期、今天页、教学周、组件使用同一结果。重复同步不得把用户校正的日期改回推算值。

### 课表读取的来源与生命周期

现有页面把消息桥挂在整个登录导航过程中，导航允许全部 `*.upc.edu.cn`，判定课表页只检查路径字符串。应分别定义“登录导航允许的实际站点”和“允许读取课表/接受消息的数据来源”。

- 课表读取固定到实际 `https://app.upc.edu.cn` 的业务页面和端点；核验 scheme、host、port 与路径，不能用 URL 包含某字符串作依据。
- CAS 等登录页只负责登录导航，不向其暴露课表数据桥。避免对所有学校子域或子框架开放桥；采用能校验来源及主框架的机制，核对现有 AndroidX WebKit 兼容性，勿为此升级整个架构。
- 固定只读请求、一次性请求标识、响应大小上限、超时和取消要共同生效。页面跳转、销毁、重登后迟到回调必须丢弃，不能污染新一轮同步。
- 相关依据：[Android WebView 消息桥说明](https://developer.android.com/privacy-and-security/risks/insecure-webview-native-bridges)。现有取消异常已重抛，继续保留，不要误当成普通错误吞掉。

### 图书馆新状态必须显示到 UI

已有严格解析、座位与时段核对、待确认和旧数据保留的改动，先完成这些改动，不重复实现另一套。

- “我的预约”显示最后成功时间、刷新失败、旧数据和待确认状态。失败不等于没有预约。
- 预约/取消请求发出、服务端返回、查询核对成功分别处理。只在可靠核对后显示最终成功；断连或超时给“结果待确认”及手动核对入口。
- 取消后刷新失败不能清空列表；核对新预约必须包含座位身份、完整日期时段，并排除提交前已有记录。不能自动重试预约或取消。

## 2. 会话复用与课表闭环是这版的主要体验目标

用户提出的“成功认证一次后重复使用”应落地为有效会话复用，不保存密码，也不承诺永久登录。

### 会话

- 分别管理课表业务 Cookie、图书馆业务 token 和必要的 SSO 生命周期。CAS ticket、OAuth code 等临时交换凭据不作为长期令牌。
- 先修图书馆登录页的全局 `removeAllCookies()`：登录成功或页面销毁不能把课表及其他业务登录一并清掉。业务退出与“退出全部学校账号”要有不同语义。
- 提供“记住登录”；App 管理的持久凭据使用 Keystore 保护的加密存储、排除备份。关闭时清理持久副本，按实际会话方式处理内存及 WebView 存储。
- 显式核对 CookieManager 的磁盘持久化行为；不能只加密原生 token 后宣称 WebView 中的 Cookie 也已加密受控。选定一种可验证的会话承接与清理方式，记录实际边界。
- 重启后首次查询验证会话；有真实刷新协议才刷新，否则按官方流程重新登录。不通过后台保活强行延长会话。
- 业务会话或 Cookie 按实际域、路径、期限和账号隔离，不将同一个 token 发往其他业务。切换账号不能显示前一账号的个人课表、余额或预约；保留自定义日程。
- 本地密钥失效/凭据损坏时清理对应凭据并重登，不能崩溃或清空用户全部日程。参考：[Android Keystore](https://developer.android.com/privacy-and-security/keystore)。

### App 内课表流程

- 保留当前方案：“App 内官方登录 → 原生选学期 → 串行读取整学期 → 原生预览 → 确认写入”。登录页不读取密码，不让用户为了日常同步安装脚本。
- **先核对数据契约**：暂停代码使用 `get-data/type=1`；第三方源码使用 `get-datatmp/type=1`；旧脚本另有分组数据结构。以学校当前实际页面请求和返回为准，分别验证，不能混用某个端点的字段假设。
- 一周出错、过期、格式异常或取消，均保持原数据库；合法空周与错误响应分开。空学期替换应专门确认，避免误删已有学校课程。
- Room 事务只替换指定学期的学校来源，保留自定义/CSV 数据和显示覆盖，重复同步幂等。检查课程与会话标识是否能区分同名课程及同一课程的不同上课时段。
- 第 14 节只能在确有需要时由用户补时间，不编造 UPC 官方作息。验证网格、编辑、详情、今天页、组件和导入限制一致。
- CSV/剪贴板保留为备用；外置脚本严格校验的修补排在主流程收尾之后，不能继续把脚本作为默认同步入口。

## 3. 图书馆收尾，保留空教室

- 图书馆目前已有原生数据层和界面，不推倒重做；验证业务 token 交换、当前用户、馆区、日期、座位图、时段和“我的预约”。登录页出现不是登录验证完成。
- 真实预约或取消只能由用户明确确认触发。没有本人账号实测时，交付中明确列出待验步骤，不凭合成测试宣称预约成功。
- `libseat` 与新资料中的超星空间预约保持两个入口。先确认关系和馆区，不在本版额外实现第二套预约系统。
- 保持已工作的公开原生空教室查询：两校区、日期、楼栋、节次和结果时间；无需预约。不要因新文档只做匿名页面检查，就抹掉之前已有的真实查询验证记录；验证结论注明各自日期和范围。

## 4. 余额推进方式：修正旧结论，再做有目标的核查

| 系统 | 当前有证据的事实 | 下一项可消除不确定性的工作 |
| --- | --- | --- |
| 唐岛湾电费 | 官方入口匿名跳微信 OAuth | 从学校正常服务入口核对授权后业务会话、只读请求、续用和回调可能性；不把一次性 code 存成固定参数 |
| 古镇口电费 | 有官方域名 `https://gzkdf.upc.edu.cn/acmswx/index.aspx`，本机记录为证书过期 | 复核证书状态、学校新入口及校内可用性；不再写“无公开域名” |
| 校园卡 | 已知裸链接返回错误，不是余额 | 从校园卡服务大厅正常进入，确认有效会话和只读取数；核对金额单位与账号范围 |

- 匿名结果不足以证明“没有可用接口”“只能微信”或“CAS 可用于所有系统”。每项记录卡在入口、认证、取数还是语义，给出下一项具体核查。
- 证书错误不能用 `trustAll`、忽略主机校验或 `SslErrorHandler.proceed()` 绕过；HTTP 入口核查是否有官方 HTTPS 版本，不全局放开明文。
- 确认正常可用的只读链后才实现独立余额 Provider，原生显示余额、单位、账户/房间范围和最后成功时间。失败不显示零；缓存不冒充实时值。无充值、流水或后台采样需求。
- 微信 SDK 类型存在与目标服务可达是不同证据；缺少已验证能力时不以 `OpenWebview` 作为产品依赖。也不把“没有官方使用说明”扩大为“已证明绝对不可行”。可用官方小程序/链接有真实来源时单独验证。
- 复制/分享/启动微信主页准确标为备用动作，不标“直达”。本轮不继续投入无配置、无目标服务证据的 SDK 界面。
