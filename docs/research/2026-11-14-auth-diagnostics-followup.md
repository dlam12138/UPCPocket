## 真实账号定位结果

用户明确授权后，主控从既有本机加密凭据源在内存取用真实账密，在隔离的 API 36 模拟器验收最终长期签名 Release。没有将账密、账号标识、Cookie、Token、HTML、响应正文或个人业务内容写入证据。用户指定来源会话的 APK 与本轮开工时设备安装包核对一致；该来源 APK 的 SHA-256 为 `b5ca354c38c1bf5b130687a7f28db28f4ee1abb3c3ad0b7eca387825216d949e`，与其他历史同版候选分别记录。

真实流程暴露了两处客户端假设错误：

1. 公共 CAS、校园卡与石光表单解析把 `execution` 限制为 4096 字符。实际普通密码页的字段超过此值，导致密码提交前拒绝表单，进入交互回退。三处现共用 `isValidCasExecution()`，上限为 65,536；非空、空白/控制字符、固定 HTTPS 主机、service、action、回跳、响应大小与单次 POST 限制继续校验。
2. e站通已经完成密码认证与业务回调，但客户端会话检查错误要求 `d.num` 为整数；实际成功信封的 `d.num` 为数组。现检查严格整数 `e == 0` 与 `d` 对象，并保留已发送业务 Cookie、固定回调、受控认证来源和账号/凭据代次绑定。`num` 不作为认证条件，也不据此推测其业务结构。成功信封本身不能单独证明本人身份；归属依据受控密码认证与业务会话绑定链。

本次证据指向客户端解析和会话判定，不能据此断言学校服务端发生了变化。“逆向未发现明显变化”不足以证明合并后的安装包可以自动登录。此前真实验证曾覆盖部分服务和中间产物，未覆盖用户拿到的最终合并 Release 四项页面，这是此前验收的缺口。

统一的是学校账号、加密保存、凭据代次及 CAS 基础设施。课表和 e站通复用通用 CAS 流程，流水和石光仍有业务专用认证适配，负责各自的回调、Cookie、本人核验和会话接纳；不能把这四项描述为完全同一个实现。公开查询及本机功能也不以 CAS 作为共同前提。
