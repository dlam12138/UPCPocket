### 1.1 2026-11-03 补充：现有 Edge 会话可用，不能由无 Cookie 探测否定

用户提供的当前 Edge 截图和本轮只读 UI 观察都显示：求是图书馆研讨间
`reserve.chaoxing.com/front/web/apps/reservepc/index` 已在现有 Edge 中正常打开，页面
显示“研讨室列表”及 A301、A402–A404、A501–A505 等房间。窗口标题为“【求是图书馆】研讨间预约”。

地址栏只记录参数名、不记录值：`reserveId`、`resvAppId`、`enc`、`fidEnc`、`uid`、
`wfwEnc`、`wxAppid`、`mappId`、`appId`、`code`、`state`。这些参数说明真实入口带有
租户/授权上下文；无 Cookie 的简单 `?reserveId=...` 请求得到 303，**不能**据此判断用户
现有会话不可用或页面没有登录。必须区分：

- **无 Cookie 探测**：只能证明该 URL 形状在没有租户/会话上下文时不能复现页面；
- **现有 Edge 页面**：已加载业务列表，证明当前浏览器会话有效；
- **真实接口**：尚未取得，仍需要当前页面的 Network/Resource 证据。

因此本轮修正上一版“reservepc 当前接口不可用”的推断：页面可用，但自动化网络/DOM
证据仍缺。由于现有 Edge 没有 CDP，且不能用独立 Chrome 替代当前登录会话，下一步必须
使用当前 Edge 的 DevTools Network 或用户导出的本地 HAR。

本轮没有完成“现有 Edge 标签的实时网络捕获”。因此：

- **observation**：公开 HTML/JS/JSON、HTTP 状态、前端字符串、公开规则，以及现有 Edge
  的窗口标题/可见页面文本/地址栏参数名；
- **inference**：由前端调用点推导的参数结构、业务语义和认证顺序；
- **unknown**：现有 reservepc 实际 XHR、响应 JSON、分页、错误码和写接口；Chaoxing 其他
  入口当前接口；需要登录才可见的完整响应。

## 2. 结论摘要

1. 六个入口不是一套平台：
   - 唐岛湾座位 `libseat` 与唐岛湾东馆研讨间 `nspace` 都在 `libspace.upc.edu.cn`，共用
     学校 CAS 的正常登录入口与同一个 CAS service 形状，但业务 token、API 前缀、前端
     存储键和预约模型彼此独立。
   - 古镇口东区座位/研讨间、求是图书馆座位/研讨间在 `office.chaoxing.com` /
     `reserve.chaoxing.com`，当前入口正常跳转到 Chaoxing `passport2` 登录，不能把
     libspace 的 token 或接口复用到 Chaoxing。
2. libspace 的 CAS 登录是“入口引导 + 一次性 ticket + 业务 app token”：
   - 入口先建立 `libspace` 的 JSESSIONID 并 302 到 `cas.upc.edu.cn/cas/login`；
   - CAS 回调用同一个 service 路径，ticket 只能使用一次；
   - 回调 URL 中的 app token 再兑换为 `libseat` 或 `nspace` 自己的业务 token；
   - **不能保存或复用带 ticket/token 的回调 URL**，只能保存业务 token（加密）并在
     账号/凭据/业务代次校验后使用。
3. `libseat` 已有较完整的公开前端协议、既有真实只读验收，以及本轮 26 条 HAR 对
   `filters/floors/stats2/settings/announce/user/reservations` 的实证；未覆盖房间布局、
   时段和写接口。适合作为 M4 的唯一现有范围。
4. `nspace` 的公开前端接口已基本还原，但没有本轮登录态下的真实响应；应作为独立的
   新功能/后续阶段，不应因为“同一个 libspace”就假定与座位共用 token 或数据模型。
5. Chaoxing 六个入口中的四个当前只确认了登录跳转和旧版公开资料；求是 `reservepc` 已在
   现有 Edge 正常加载房间列表，但尚未取得该页面的真实 XHR/响应。当前 `seatengine`/
   `reservepc` 的接口、会话和租户参数不能进入 M4 原生实现，保留官方网页入口。

## 4. libspace 认证与会话

### 4.1 正常学校认证顺序

公开前端和 UPC-MCP 已验证的 service 形状一致：

1. 打开图书馆正常 SSO 入口：
   `https://libspace.upc.edu.cn/remote/static/sso/login?redirectUrl=<应用登录页>`。
2. 该入口返回 302 到 `https://cas.upc.edu.cn/cas/login`，`service` 为：
   `https://libspace.upc.edu.cn/remote/static/casAuth/getServiceByVerifyTicket/casLogin`。
   入口响应同时下发 libspace 的 JSESSIONID；回调需要同一入口会话。不同应用使用不同的
   `redirectUrl`，但当前观察到相同 CAS service 路径；目标应用由入口会话/回调上下文区分，
   不能把 `libseat` 的 ticket 拿去换 `nspace` 的 token。
3. 在 CAS 正常表单提交一次账号密码；出现图形验证码、二次验证、异常错误页时停止自动
   提交，转学校正常网页登录。不能循环试密码。
4. CAS 302 回 libspace 的 service 路径并携带一次性 ticket；只跟随
   `libspace.upc.edu.cn` 的预期路径，拒绝其他主机、路径、重复 ticket 参数和非 HTTPS。
5. 回调完成后，业务页面 URL 或页面脚本会得到 app token；该 app token 再兑换对应应用的
   业务 token：
   - `libseat`：`POST /rest/ssoAuth?token=<app_token>`，表单也带 `token`，响应
     `data.token`；
   - `nspace`：`GET /spa/static/public/api/remoteCasLogin?token=<app_token>`，响应
     `data.token`、`data.userInfo`、可选 `data.teamConfig`。
6. 业务 token 还要调用本人接口核对（`libseat` 的 `/rest/v2/user`；`nspace` 的
   `remoteCasLogin` 响应中的 `userInfo`），并与当前统一账号身份比对后才可发布/落盘。

前端存储键（只记键名，不记值）：

| 应用 | sessionStorage 前缀 | token 键 | 其他键 |
| --- | --- | --- | --- |
| libseat | `libseat-m-` | `libseat-m-token` | `libseat-m-loginType`、`libseat-m-userInfo` |
| nspace | `spa-p-` | `spa-p-token` | `spa-p-loginType`、`spa-p-userInfo`、`spa-p-teamConfig`、`spa-p-vueConfig` |

现有 Android 图书馆登录回退只捕获 `libseat-m-token`；如果未来接入 `nspace`，不能复用这
一段捕获逻辑，必须单独读取 `spa-p-token` 并按 nspace 的 `remoteCasLogin` 流程兑换。

### 4.2 请求头与会话失效

- `libseat` 所有业务请求带 `Authorization: <token>`、`loginType: PC`；前端公开配置启用
  `X-request-id`、`X-request-date`、`X-hmac-request-key` 签名。签名密钥来自页面公开配置，
  不是用户凭据；本项目已有 `LibrarySeatProtocol` 实现，本文不复制密钥或算法细节。
- `nspace` 业务请求带 `Authorization: <token>`；没有观察到与 `libseat` 相同的 HMAC 头，
  但当前没有登录态响应，不能断言服务端不校验其他头。
- 失效语义：
  - `libseat` 业务 JSON `code=12` 表示 token 过期；HTTP 401/403 也是认证失败。前端清理
    `sessionStorage` 后回登录页。
  - `nspace` HTTP 401 或响应 `code=401` 时清理存储并按 `loginType` 重新进入 CAS；
    `code=200` 为成功。
  - 两者都不能把 401/403、验证码或网络失败解释成“空列表/没有预约”。

### 4.3 为什么不能复用一次性 URL

CAS ticket 和回调中的 app token 都是一次性、短时、可识别会话的材料。把回调 URL 保存为
“长期登录方案”会同时违反票据一次性、账号隔离和清理要求。长期只允许保存业务 token，
并且必须绑定 `(accountId, credentialGeneration, businessGeneration)`；换号、删号、改密、
清理失败和插件隔离时都要能删除，不得从旧 URL 恢复。

### 5.1 响应与错误语义

- `status == true` / `success` 是成功；`code=12` 是 token 过期；HTTP 401/403 是认证失败；
  `code=20` 需要结合签名/时间排查，不能直接解释成“功能停用”。
- 当前预约 `data:null` 是明确空态；缺 `data`、对象/字符串等异常类型必须报协议错误，
  不能显示成“没有预约”。
- 座位可选条件：`type=seat`、`enabled=true`、`local=false`、`status` 为 `FREE` 或
  `YESSELECT`。`IN_USE`、`BOOKED`、`FULL`、`AWAY` 等不能当成可用。
- 布局 key 可能编码为 `row*1000+col`，也可能显式 `row/col`；两种都要按来源处理，不能
  把未知 key 猜成座位。
- 空房间列表不等于“全部可约”；失败/认证过期也不能显示成空周或空预约。

### 5.2 公开规则（摘要）

`/rest/v2/announce` 当前公开规则写明：当天 06:00–21:30、次日 18:00–22:00 可预约；每天
最多预约 5 次、取消 5 次；预约座位需在校园网内使用；普通座位最长 4 小时，总馆四/五楼
和东馆二楼 24 小时学习区有 16 小时例外；开始前后 30 分钟内签到；暂离保留 30 分钟
（午/晚饭时段 60 分钟）；累计违约有禁用处罚。规则可能随学校调整，应用必须显示来源时间，
不能把本文当成永久规则。

## 8. M4 范围建议

1. **M4 保持 libseat 单入口**：只把现有图书馆座位（唐岛湾）接入统一学校账号、正常 CAS
   和 WebView 验证码/二次验证回退。保留现有查询/预约/取消页面与交互，只增加认证状态和
   必要回退界面。
2. **nspace 另立范围**：虽然同属 libspace 且共用 CAS service，但它是独立业务 token、
   独立 `/spa` API、独立预约模型和独立规则。至少在取得一次正常登录态下的只读证据
   （馆区/空间/日期/时段/本人记录）后，再决定是否并入 M4；不能把 nspace 当作“座位接口
   的另一个路径”。
3. **Chaoxing 暂不原生接入**：四个入口继续保留官方网页入口；如果后续要做，先满足：
   - 在用户现有登录态下用 CDP/REA 捕获一次正常只读请求（需要用户同意开启调试或提供
     受控录制）；
   - 确认租户/入口参数和登录来源，不把一次性 `casreceive`/ticket 当长期认证；
   - 只读接口先验收，写接口单独评审；
   - 不复制旧版 `enc` 或猜测签名。
4. **认证实现原则**（若恢复 M4 编码）：
   - `core:upc-auth` 增加受控的 libspace CAS/provider，只向 feature 返回业务 token 或
     经校验的会话，不暴露密码/通用解密；
   - 普通 feature 只依赖 `core:account-api` 与 `core:upc-auth`，不依赖 `core:account`；
   - 登录入口捕获 `(accountId, credentialGeneration)` 和业务代次；网络在锁外，最终写入
     在业务提交门闩内复核；
   - 换号/删号/改密/清理失败时清 libspace token、WebView 学校 Cookie 和相关个人数据；
   - CAS 验证码/二次验证时打开学校正常网页，完成后只采用业务 token，不保存密码或票据。
