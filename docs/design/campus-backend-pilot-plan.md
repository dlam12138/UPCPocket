# UPC Pocket 校内后端建设计划书

Android 首期方案（现有校园接口不变 · 账密由校方服务器托管）

UPC Pocket 项目组　｜　供信息化建设处及相关部门讨论　｜　2026 年 11 月 27 日

## 一、先说清楚：我们要改什么、不改什么

项目转由学校主导后，我们采用**改动最小、落地最快**的方案：**学校现有的各个业务系统接口保持不变**，只把原本存在学生手机本地的学校账密，统一挪到**校方提供的服务器上加密托管**，由校方服务器代为向现有校园系统发请求，再把结果返回手机。

**Android 手机 → 校方 HTTPS 网关 → Pocket 后端（托管加密账密） → 现有 CAS 与校园接口**

这样做有两个直接好处：
1. **不折腾现有校园系统**：课表、校园卡、图书馆、成绩、石光、e站通都继续复用 App 里已经跑通的现有接口，不用等各个业务部门重新开发新 API。
2. **账号安全收归学校统一管**：学生手机本地以后不再保存学校密码；账号库和密钥全在学校机房，校方随时能审计、能停用、也能在学生开发者毕业后平稳接管。

### 本期范围与边界

| 部分 | 怎么安排 | 说明 |
| --- | --- | --- |
| 现有校园接口 | 保持不变 | 继续走学校现有的 CAS 登录及各业务系统接口，不要求教务、一卡通、图书馆等部门改造接口。 |
| 校方托管内容 | 只存加密账密与状态 | 校方服务器只长期保存加密后的学生账密和账号启停状态；课表、余额、流水、成绩等业务正文**不落库**。 |
| 客户端范围 | 首期先改 Android | 后端接口按通用方式设计，后续做原生 iOS 应用可直接复用，不用在 iOS 里重复写各套校园登录逻辑。 |
| 本机工具与开发 AI | 均不上传学校数据 | 待办、专注、个人日程继续只留在学生手机本地；国产大模型只供开发团队写代码和文档，不进 App，也不接触任何真实学生数据。 |

现状对照：现行 Android 版由手机加密保存学校账密后直连各校园服务。[现行账号与会话架构](../../ARCHITECTURE.md#本机账号与业务会话) · [项目隐私说明](../PRIVACY.md#学校账号) · [现有学校服务入口目录](../upc/官方入口.md)

### 启动前，最需要学校先配合的四件事

1. **定对接人与部署资源**：确定牵头单位和校方运维负责人，提供测试/生产服务器、HTTPS 网关、独立数据库及密钥托管方式。
2. **给后端服务器出口 IP 加白名单**：以前是几千台手机各连各的，改成一台校内服务器集中访问现有 CAS 和业务接口后，容易触发学校的防爬虫限流或频繁弹验证码，需要信息化建设处提前给后端出口 IP 放行。
3. **定账密管理规矩**：明确账号停用、学生解绑删除、备份保留多久，以及生产运维的审批与审计流程。
4. **走校方合规备案**：请校方提供现行的《信息系统建设集成规范》和备案流程；按学校现行办法需要提交的申请、协议、保密承诺或安全评估材料，我们按校方要求补齐。[校方数据管理办法第 17、18、23、24 条](https://nic.upc.edu.cn/_upload/article/files/6c/9e/2a94c6d147b6b1db688e86dac858/7bf8e886-e435-4ea6-b403-5bf10cdf08bd.pdf#page=5) · [信息系统建设集成规范入口](https://nic.upc.edu.cn/2026/0312/c7408a484506/page.htm)

## 二、手机发起一次查询，后台怎么走

1. **绑定与登录：密码只交一次，手机不再存密码。** 学生首次启用或修改密码时，通过 HTTPS 把数字石大账密提交到校方服务器，后端立刻拿它向现有 CAS 跑一次真实校验；验证通过后，校方服务器把账密加密入库，只给手机发一张**可随时作废的 Pocket 登录凭证**。之后密码**永远不回传手机**。
2. **日常查询：后端按当前登录人代调现有接口。** 手机查课表、校园卡余额/流水、图书馆座位、成绩、石光或 e站通时，只带自己的 Pocket 登录凭证和业务参数（如第几周），**接口里不让客户端随便传别人的学号**。后端先复用内存里还没过期的该业务短期会话；会话过期时，才按当前登录身份单条解密账密，走现有 CAS 换取新会话，并在内存里立刻清掉明文密码。
3. **结果返回与异常处理：不留正文、不乱报错。** 后端把必要结果整理好返回手机，服务器不存业务正文。上游报错或超时时，手机老实提示查询失败，有本机旧缓存就展示旧缓存并标明时间；如果现有 CAS 依然触发验证码或二次验证，不硬绕，按现有机制提示或交由官方网页处理。
4. **高风险写操作守住原底线。** 校园卡微信充值依然只做查单与拉起微信，实际付款由学生在手机微信里本人确认，后端不存支付链接或付款凭证；图书馆预约必须由学生在界面最终确认后单次提交，超时或结果不明绝不自动重试。

### 各类数据分别存在哪儿

| 数据类型 | 放哪儿、怎么管 |
| --- | --- |
| 加密账密与账号状态 | 存在校方服务器独立的加密账号库里，逐条加密保存。只允许按已验证的本人身份单条读取用于代登，禁止批量导出，也绝不回传给手机。学生解绑、删号时按校方规定清除密文。 |
| 业务短期会话（Cookie/Token） | 仅在后端服务器内存里短时保存，用来减少重复解密密码的次数；不写硬盘、不进备份。用户退出、踢设备、改密、解绑或校方停用账号时立刻作废。 |
| Pocket 手机登录凭证 | 服务器端只把随机凭证的单向摘要和过期时间放在内存里（不存原文、不落盘）；手机丢失可单独踢掉某台设备，学校停用账号时全端立即失效。 |
| 课表、余额等业务正文 | 只在查询瞬间过一下服务器内存，不进校方业务库、不进日志和公共缓存；离线副本按账号隔离存在学生自己手机里。 |
| 本机个人工具数据 | 待办、专注、个人日程、主题与个人隐藏座位等，继续只保存在学生手机本地，不上学校服务器。 |

## 三、服务器怎么把“存账密”的安全系数拉高

既然校方服务器要集中托管学生账密，最核心的防线就是两条：**防止账密被一锅端**，以及**确保开发者和管理环节谁也随便看不了密码**。

首期结构尽量简洁、方便学校运维长期接手：**一个 Pocket 后端程序**（内部分账密托管、会话管理、校园业务转发三个模块）配**一个独立的加密账号库**。技术栈优先顺着校方运维习惯选；如未指定，可沿用团队现有 Kotlin 经验，采用 Spring Boot + PostgreSQL。

- **密码只进不出、主密钥与库分离**：每条账密使用独立随机盐/数据密钥做强加密（信封加密），主密钥交给校方独立托管（KMS 或校方专用密钥存储）并定期轮换，不写进代码或配置文件。业务代码只提供“按本人会话单条使用”的受控能力，明文仅在请求瞬间驻留内存并用完即清零。
- **网络锁死、环境彻底分开**：对外只暴露校方 HTTPS 网关，后端程序和账密库全放校内受限内网，内网通信照样校验证书。开发、测试、生产三套环境物理或网络隔离，**学生开发者拿不到生产密钥，也查不到线上真实账密库**。生产操作必须实名账号加二次验证，临时权限到期自动收回。
- **全链路防泄露、日志不留底**：个人业务接口全部关闭公共缓存；网关、应用日志、错误监控一律屏蔽密码、Cookie、票据、查询参数和业务正文，并关闭请求正文落盘。排障日志只记三项：**随机请求编号、固定结果状态、耗时**。运维人员的所有敏感操作由校方独立审计。
- **顺带留一条无密码升级路**：如果后续信息化建设处愿意开放 CAS 代理票据（Proxy Ticket）或官方免密接口，后端只需替换认证模块就能彻底去掉密码存储，手机端接口不用大改；但**首期不卡在等学校改接口上**。

### 三方分工：控制权归学校，开发与运维分开

| 参与方 | 主要负责什么 |
| --- | --- |
| 信息化建设处及校方运维 | 掌管域名、证书、网关、服务器、账密库、主密钥、出口白名单和生产权限；定安全评估、审计留存、应急联系人和撤权时限；负责正式发布、一键停用和灾备恢复。 |
| 相关业务系统接口方 | 无需改动现有业务接口；配合确认后端出口 IP 放行或合理调用频率，若校园接口调整或出现异常，及时同步运维排查。 |
| UPC Pocket 项目组 | 开发 Android 端和后端程序，交接接口说明、部署手册和回滚方案；只在隔离测试环境联调，动生产环境必须经校方审批；开发用 AI 工具绝不接触真实账密或学生数据。 |

### 老用户怎么切换、出问题怎么兜底

- **平滑切换，旧本地密文清理干净**：升级后学生主动走一次校方后端登录并校验通过，旧版本留在手机本地的密码密文和旧会话立即清理，之后手机不再存密码。
- **换号不串人，删号不伤本机记录**：切换或解绑账号时，立刻撤下上一个账号的课表、余额缓存和桌面小组件，晚到的旧请求结果直接丢弃；学生的本机待办、专注和日程完整保留。上线前更新隐私说明，把“账密存在校方服务器、请求经校方服务器转发、怎么解绑删除”写清楚。
- **一键止损与退出机制**：校方停用某人账号后，后端立即作废其会话，离线手机一联网发现被撤权即清掉对应业务缓存与组件。万一发现串号、异常调用或泄露风险，校方运维直接一键停用后端入口或冻结受影响模块并通知学生，排查复核后再恢复；期间学生照常可以打开学校官方网页，或使用本机待办和专注。

## 四、五周推进节奏与验收标准

以下按**校方服务器、网段与白名单到位后五周**给出参考排期；服务器规格、容量与经费由校方按试点人数核定，测试和生产环境分开部署。

| 阶段 | 谁牵头、做什么 | 这一步交什么、怎么算过关 |
| --- | --- | --- |
| 第 1 周 · 定边界与环境 | 信息化建设处牵头，落实测试主机、密钥托管、出口白名单与合规手续。 | 确认服务器与内网边界、主密钥托管方式、出口放行清单、账密管理规则和隐私告知文案。 |
| 第 2 周 · 通账密托管 | 项目组打通 Android 绑定/改密/退登、校方加密入库、单条使用清零和撤权。 | 测试环境演示真实账号绑定、踢掉单台手机、改密、解绑删密文、校方一键停用——**账密服务可先独立验收**。 |
| 第 3–4 周 · 迁现有业务 | 依次把课表、校园卡、图书馆、成绩、石光/e站通等现有接口转发迁入后端并改好客户端。 | 交付完整转发清单、换号隔离记录、验证码回退与充值/预约防重核对记录、运维部署与回滚手册。 |
| 第 5 周 · 小范围试跑 | 校方组织小范围真实账号试用，运维和项目组一起核对稳定性与安全边界。 | 输出脱敏验收报告、白名单压测与异常记录、遗留问题清单，由校方拍板是否全面开放。 |

### 试点现场怎么算真正通过

1. **账密“只进不出”且撤权立刻管用**：两名获准参与的同学用本人真实账号完成绑定。抓包与本机存储检查确认手机不再留存或回传学校密码；退出登录、踢掉某台手机或学校后台停用账号后，旧会话在约定时间内失效；解绑删号后库内密文按约定清除。
2. **现有功能准确、换号绝不串人**：两位同学各自核对课表、校园卡余额等常用功能，结果与学校官方系统一致，集中出口未触发异常封禁。切换账号后，页面和桌面小组件立刻只显示当前账号的数据，晚到的旧请求被丢弃。验收文档只记结论，不留真实个人数据截图。
3. **服务器不留业务正文、故障老实提示**：用一条专门造出来的测试标记跑完查询，核对数据库、日志、缓存和备份，确认里面没有明文密码，也没有任何课表、流水等业务正文。在测试环境模拟上游超时或验证码时，手机老实报错、展示带时间旧缓存或回退官方页。
4. **学校运维能独立接管**：校方运维照着交接手册，独立演练一次停用入口、撤销会话、密钥轮换，并在隔离环境里把加密账密库备份恢复出来。项目组交回试点期间的临时权限。

账密托管服务与业务转发可以分阶段签验收。上线后如需新增校园功能或切换为学校统一认证免密接口，均沿用同一套“校方审批、隔离测试、可一键停用”的机制推进。
