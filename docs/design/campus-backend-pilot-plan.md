# UPC Pocket 校内后端建设计划书

Android 首期试点方案

UPC Pocket 项目组　｜　供信息化建设处及相关业务部门讨论　｜　2026 年 11 月 27 日

## 一、先说清楚：我们要建什么、首期做多大

项目转由学校主导后，我们建议把后端直接部署在学校提供的服务器上，跑一条最清晰的链路：**学生用手机发起请求 → 校方服务器按当前学生本人的权限去查学校对应系统 → 把结果返回给手机**。

为了稳妥落地，首期只做两件事，而且**两件事可以分开审批、分开验收、分开开关**：

1. 先把**账号登录和设备管理**跑通（能登录、能退出、能踢掉某台手机、学校后台能一键停用）。
2. 等教务部门批准后，再接一个最常用的只读功能——**“查我这周的课表”**，拿它把整条链路走通、验稳。

### 首期试点安排

| 阶段 / 模块 | 具体做什么 | 什么时候可以开 |
| --- | --- | --- |
| 账号服务 | 学生在学校官方页面完成登录，App 拿到只属于自己的登录凭证；支持退出登录、单独踢掉某台手机，也支持校方随时停用账号。首期优先上线。 | 校方确定账号里要存哪些字段、用哪种登录协议，以及停用账号后多久生效。 |
| 本人课表 | 手机按学期和周次查本人课表，只返回课程名、节次、上课地点，以及学校数据的更新时间（如果上游提供）。作为首期试点业务。 | 教务部门确认开放范围和允许返回的字段，校方提供“只能查本人”的只读接口。 |
| 后续扩展 | 校园卡余额、图书馆查询等只读功能，以后照同一套模式接就行；涉及花钱或占座的充值、预约，到时候单独设计确认、防重复提交和查单核对。暂不在首期。 | 按业务逐项报批、逐项验收，通过一个上一个。 |

### 现在是什么情况、这次覆盖什么范围

目前的 Android 版没有项目自建后端，手机直接连学校各个页面，用户也可以自己选择把学校账密加密存在手机本地。这次试点**先只改 Android 端**，接口会留好通用性，以后做原生 iOS 应用可以直接复用。另外需要说明：国产大模型只供开发团队平时写代码、整理文档用，**不会塞进 App 里，也不会接触任何真实学生数据**。[现行账号与会话架构](../../ARCHITECTURE.md#本机账号与业务会话) · [项目隐私说明](../PRIVACY.md#学校账号)

### 启动前，最需要学校先拍板的事

1. **定对接人**：确定牵头单位，以及统一认证和教务接口的负责人。
2. **定清楚“只存账号”到底存什么**：目前共识是“只有账号信息存在学校服务器上”，会上最需要确认的是这里面**包不包括数字石大密码**（我们强烈建议不存密码，下面第二部分有详细对比）。
3. **走校方合规流程**：请校方提供现行的《信息系统建设集成规范》和试点办理流程。按学校现行的《信息系统数据管理办法（试行）》，接入数据平台需要提交数据使用申请、签使用协议和保密承诺，正式接入前还涉及技术备案和第三方安全评估，相关材料我们按学校要求准备。[校方数据管理办法第 17、18、23、24 条](https://nic.upc.edu.cn/_upload/article/files/6c/9e/2a94c6d147b6b1db688e86dac858/7bf8e886-e435-4ea6-b403-5bf10cdf08bd.pdf#page=5) · [信息系统建设集成规范入口](https://nic.upc.edu.cn/2026/0312/c7408a484506/page.htm)

## 二、一次“查本周课表”具体怎么跑通

**Android 手机 → 校方 HTTPS 网关 → Pocket 后端 → 校方数据平台或教务接口**

1. **先在学校官方页验明身份。** 点登录后，App 拉起系统浏览器打开学校官方登录页，学生只在学校页面里输密码。不管学校提供的是 CAS（用完即作废的一次性票据）还是 OpenID Connect（走授权码加 PKCE 防拦截，限定已登记的回调地址，并核对签名、签发方、适用范围和有效期），都必须由 Pocket 后端核验无误后，才给这台手机签发一张可以随时作废的登录凭证。[CAS 服务票据规范](https://apereo.github.io/cas/development/protocol/CAS-Protocol-Specification.html#311-service-ticket-properties) · [原生应用登录规范](https://datatracker.ietf.org/doc/html/rfc8252) · [OAuth 安全规范](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.1.1)
2. **后端按登录身份查本人课表，不认客户端传的学号。** 手机发请求（如 `GET /v1/me/timetable`）时，只传“哪学期、第几周”，**接口里压根没有填学号的地方**。到底查谁的课表，完全由后端根据当前有效登录身份确定，再由教务授权或校方数据平台在服务端卡一道“仅限本人”的关。就算有人反编译改了 App，也查不到别人的课。如果学校现有数据共享方式是整表同步，建议先由校方数据平台包一层“按本人取数”的接口，避免把全校课表交到应用端。
3. **只把必需内容发回手机，报错绝不当成“没课”。** 后端在内存里把课程名、节次、地点整理好发回手机。只有学校上游明确返回“这一周完整且没课”时，手机才显示“本周无课”；如果学校接口超时或出错，App 会老实提示查询失败，手机里若有以前缓存过的课表，就展示旧课表并标明是什么时候查的。

### 各类数据分别存在哪儿

| 数据类型 | 放哪儿、怎么管 |
| --- | --- |
| 账号基本信息 | 存在校方服务器的 Pocket 账号库里，**只记三样**：应用内部编号、学校给的唯一标识、账号当前是否启用。业务确需学号时，由学校接口在后台做受控对应。账号停用、解绑、删除以及备份保留多久，按校方规定执行。 |
| 密码与校方会话 | **强烈建议不存数字石大密码**，登录始终走学校统一认证页面。如果后续真遇到老系统必须代登录，这项能力单独审批，由学校统一认证团队用专门的凭据服务来管，不放进 Pocket 自己的业务库。 |
| Pocket 登录凭证 | 学校发的一次性登录票据用完立刻作废。Pocket 给手机发的随机登录凭证，服务器端只把加密后的单向摘要和过期时间临时放在内存里，不写硬盘、不进备份。凭证过期或服务重启后，学生重新登录即可。 |
| 课表与本机数据 | 课表正文只在查询那一瞬间过一下服务器内存，不落库；离线副本按账号分开存在学生自己手机上。待办、专注、个人日程继续只留在本机，不上传学校服务器。 |

关于数据新鲜度还有个小细节：学校 2024 版数据共享目录里，本科生和研究生课表都是**每天同步一次**。如果试点用的是这份数据，手机界面会把“学校数据的更新时间”和“刚才查询的时间”分开标清楚，避免学生以为刚调的课立刻就同步好了；如果上游没给更新时间，就只标本次查询时间。[校方共享目录，本科见第 30 页、研究生见第 50 至 51 页](https://nic.upc.edu.cn/_upload/article/files/26/68/103edc744faa995d4b1ae5175dad/99a919b1-1c70-4d57-8398-174b5ad0c714.pdf#page=30)

## 三、谁来管、怎么防风险、老用户怎么切

### 三方分工：控制权归学校，开发与运维分开

| 参与方 | 主要负责什么 |
| --- | --- |
| 信息化建设处及校方运维 | 掌管域名、证书、网关、服务器、密钥和生产环境权限；确定安全评估、审计日志留存、应急联系人和停用生效时限；负责正式上线、紧急关停和恢复。 |
| 教务等业务主管部门 | 确认开放给哪些学生、允许返回哪些字段、数据多久更新一次以及调用上限；提供只读接口和核对依据；授权有变化时通知运维并复核权限。 |
| UPC Pocket 项目组 | 负责开发 Android 端和后端程序，交接接口说明、部署手册和回滚步骤；只在隔离环境里开发联调，进生产环境必须经校方授权；开发用的 AI 工具只接触代码、公开资料或编造的测试样例，不喂真实数据。 |

### 服务器上重点防哪几件事

首期系统尽量做轻、方便学校长期接手：**一个后端程序**（内部分认证、会话、课表三个清晰模块）配**一个独立的账号关系数据库**。技术栈优先选学校运维顺手的；如果学校没有指定，可以沿用团队现有的 Kotlin 经验，上 Spring Boot + PostgreSQL。

- **把网络和接口权限锁紧**：对外只开放校方 HTTPS 网关，后端服务和账号库全放内网；内网调用也照样校验证书。每个校园业务只允许连事先登记好的地址和方法，各自独立配服务账号、限流和超时，互不串联。
- **把密钥和人员权限管死**：各类服务密钥交给校方托管并按业务定期轮换；开发、测试、生产三套环境彻底分开。进生产环境必须用实名账号加二次验证，临时权限到期自动收回。账号库和备份都加密，并且由校方演练确认能真正恢复出来。
- **不让课表正文偷偷留在服务器里**：个人查询接口关掉公共缓存；网关、后端日志、监控和报错链路一律过滤掉登录票据、查询参数和请求/响应正文，同时关掉相关的临时落盘。排障日志只留三项：**随机请求编号、固定结果状态、耗时**。运维人员的操作由校方单独审计。

### 老用户怎么切换、出问题怎么兜底

- **平滑切换，旧密码不上传**：老版本用户主动点登录，去学校官方页重新认证即可。原来保存在手机里的密码、密文和 Cookie 留在原设备，绝不往服务器上传。
- **换号不串数据，删号不伤本机记录**：切换账号时，马上撤掉上一个账号的课表和桌面小组件，就算之前的查询结果晚几秒返回也直接扔掉。学生清理学校账号时，个人的待办、专注和日程会完整保留。试点前我们会把“账号存哪儿、数据怎么走、怎么解绑”写清楚告知参与者。
- **停用能生效、出事能一键止损**：校方后台停用某个账号后，Pocket 通过停用通知或在约定时限内复核身份，直接作废该账号的所有会话；离线手机一旦重新联网发现被撤权，会立刻清掉对应课表缓存和组件。万一发现串号或个人正文泄露，校方运维可以直接停掉受影响接口并通知学生，查清复核后再恢复开放；停用期间学生照常可以打开官方网页，或使用本机待办和专注。试点结束后，按约定清理账号和备份、收回临时权限，交接部署配置、恢复步骤和应急联系人清单。

## 四、五周推进节奏与验收标准

下面按**校方资源到位后五周**给出参考排期。启动前请校方确认可提供的网关、测试主机和密钥托管条件，并为 Pocket 划出独立的账号数据空间（测试和生产分开）。服务器配置、容量和经费由校方按试点人数和现有资源核定。

| 阶段 | 谁牵头、做什么 | 这一步交什么、怎么算过关 |
| --- | --- | --- |
| 第 1 周 · 定规则 | 信息化建设处牵头，拉通身份平台、教务和项目组敲定边界。 | 产出账号字段清单、各环节对接人、登录接入配置、课表授权申请和试点数据处理说明。 |
| 第 2 周 · 通账号 | 项目组配合身份平台，打通 Android 登录和校方账号服务。 | 在测试环境现场演示本人登录、退出、踢掉单台设备、校方停用账号——到这一步**即可独立验收**。 |
| 第 3–4 周 · 接课表 | 教务授权到位后，项目组接入本人课表、改好客户端切换并补齐交接文档。 | 交付只读接口说明、返回字段清单、换号隔离测试记录、停用与恢复操作手册。（若教务审批尚未走完，先交付账号服务。） |
| 第 5 周 · 小范围试跑 | 校方组织小范围真机试点，业务部门和项目组一起核对。 | 输出脱敏后的验收记录、遗留问题清单和处置建议，由校方拍板是否扩大范围。 |

### 试点现场怎么算真正通过

1. **登录和撤权都管用**：两名获准参与的同学各自用本人真实账号走学校页面登录。退出登录或踢掉某台手机后，旧会话在约定时间内失效；学校后台停用账号后，这个账号绑定的所有手机按同样时限停止访问。
2. **课表对得上、换号不串人**：课表阶段上线后，两位同学各自对照教务系统核对同一周的课表，确认一致。切换账号后，应用页面和桌面小组件立刻只显示当前账号的课。验收文档只记核对结论，不留真实课表截图或正文。
3. **服务器不留底、故障不误报**：运维用一条专门造出来的测试标记跑完查询，核对账号库、日志、缓存和备份，确认没有任何课表正文漏进去。在隔离测试环境里模拟学校接口不可用，手机能老实报错或展示标明时间的旧缓存，绝不把报错当成“没课”。
4. **学校运维能自己接手**：校方运维照着交接手册，独立演练一次停用试点接口、撤销试点会话，并在隔离环境里把加密账号备份完整恢复出来。业务部门确认重新开放的条件，项目组交回试点期间的临时权限。

账号服务和本人课表**分开签验收结论**。如果首期只拿到账号侧授权，验收就先落在账号服务上，课表等教务授权到位后再另排。以后每多接一项校园业务，都照这套“逐项授权、单独验收、随时可停”的流程来。
