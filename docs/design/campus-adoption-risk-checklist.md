# UPC Pocket 校方收编与全校推广潜在问题清单

供项目组内部复盘及与信息化建设处沟通前查漏补缺　｜　2026 年 11 月 27 日

这份清单梳理的是：当 UPC Pocket 从“民间小工具”转为“校方收编、全校推广的正式应用”，并采用**“现有校园接口不变 + 校方服务器托管加密账密并代发请求”**方案后，最容易在技术、安全、合规、推广和协作上踩到的坑，以及提前预防的做法。相关后端方案见 [校内后端建设计划书](campus-backend-pilot-plan.md)。

## 一、最先要防的 5 个高危坑（不提前处理最容易出大事故）

| 高危问题 | 为什么会出事 | 提前怎么防 |
| --- | --- | --- |
| 改密码后后台自动把学生账号干锁死 | 学生在数字石大官网改了密码，但校方后端还存着旧密码。如果手机桌面小组件或自动刷新定时拿旧密码去登 CAS，连错几次就会把学生账号直接锁死。 | 后端只要检测到某账号密码错误 **1 次**，立刻把该账号标记为“需重新验证”，**彻底停止一切自动/后台代登**，等学生手动输入新密码校验通过后再恢复。 |
| 校外第三方接口触发风控封 IP | 信息化建设处只能给校内系统加白名单；超星选座、微信充值 H5 等服务器在**校外**。几千人共用一个学校公网出口访问，极易被超星或微信拉黑、限流或疯狂弹滑块。 | 上线前单独实测校外接口；对强风控第三方业务留好开关，必要时保留客户端直连或一键回退学校官方网页，不要一把切死。 |
| 后端被当成“抢座外挂”中转站 | 后端接口暴露在公网后，如果只靠简单鉴权不限流，容易被抓包写成自动刷课表、刷空教室、抢图书馆座位的脚本代理，反而让校方服务器背锅。 | 按账号严格限流；选座等敏感操作保留防重、频率限制与异常告警；发现机器高频请求自动拦截并上报运维。 |
| 校园高峰把学校老系统拖垮 | 早八查课表、期末出成绩、饭点查卡、图书馆放座时，几千人同时涌入。老系统一旦变慢，后端如果死等或重复登录 CAS，会拖垮自己，更可能把教务/一卡通打慢。 | 同账号并发登录合并（只跑 1 次 CAS）；各业务独立超时和连接上限；异常时短时熔断；手机继续本地缓存优先，小组件刷新时间加随机打散（如 25–35 分钟随机）。 |
| 收编后改包名导致老用户数据丢失 | 当前正式版包名为 `com.upcpocket.next`。若校方要求改名并更换为校方新包名，系统会将其视为全新 App，老用户本机的待办、专注、个人日程和隐藏座位不会自动迁移。 | 优先争取保留原包名平滑升级；若校方确需更换包名，上线前必须先提供“本机数据导出/导入”迁移入口，避免老用户口碑翻车。 |

## 二、学校接口、网络与多人群适配问题

1. **现有接口静默改版，全校同时报错**
   - **风险**：因为不要求业务部门改造接口，本质上仍依赖现有页面/接口结构。教务、一卡通、超星或 CAS 哪天微调字段、改登录脚本，全校就会瞬间不可用。
   - **对策**：后端做轻量探活与错误聚合告警（不记业务正文）；每个业务配独立“一键降级开关”，某个接口坏了就先停用该模块并引导打开官方网页，不影响其他功能。
2. **学校系统半夜维护，被误判成“密码错误”**
   - **风险**：教务、一卡通经常凌晨维护、选课期间封网或寒暑假关停。如果后端没识别维护页或网关报错，错把维护 HTML 当成“账号密码不对”，会吓得学生乱改密码，甚至误触发账号停用。
   - **对策**：严格区分“明确认证失败（密码错）”“需要验证码/二次验证”“上游维护或网络超时”三类状态，只有上游明确返回密码错误时才提示密码问题。
3. **测试环境与生产环境的网络差异**
   - **风险**：校内测试机、生产机访问老系统时，可能存在内外网 DNS 不同、仅限校内网段、IPv6 优先、或内网使用老旧/自签证书等情况，联调能通、上线连不上。
   - **对策**：第 1 周就把生产网段的出站连通性、证书链和出口 IP 白名单逐项验证完，不要等到上线前夜再查防火墙。
4. **全校推广后的“非典型身份”踩坑**
   - **风险**：推广到全校后，除了本科生，还会有**硕博研究生**（学号含 `S/Z/M/TS/BY` 前缀，教务/培养系统可能和本科生不同）、**教职工/辅导员**（工号，没有学生课表/成绩/学生宿舍电量）、**留学生、转专业/休学复学生、新生及已毕业离校生**。
   - **对策**：提前找校方协调不同身份的测试配合或确认适用范围；对不支持某项业务的身份给出清楚直白的提示（如“当前身份暂不支持该查询”），绝不白屏或乱报“网络错误”。
5. **多设备、换手机与毕业销号**
   - **风险**：学生同时在手机和平板登录、换新手机、借给同学登、毕业离校被学校销号，如果会话和本地缓存没清干净，容易出现串号或隐私残留。
   - **对策**：支持查看并踢掉单台设备、改密全端下线；离校销号后后端按停用通知或复核机制撤销会话，离线设备重新联网即清理对应个人缓存和桌面小组件。

## 三、安全评估、合规与资金纠纷问题

1. **第三方安全评估 / 等保测评会重点盘问“存密码”**
   - **风险**：校方正式上线前通常要做安全评估或等保测评，测评人员看到库里保存学生数字石大密码（哪怕已加密），一定会追问密钥保管、能否批量导出、为什么不用免密认证。
   - **对策**：把“逐条信封加密、主密钥归校方托管、无导出接口、内存单条使用即清零、开发者碰不到生产库和密钥”落实到位，并在方案中保留“校方后续开放 CAS 代理票据或官方免密接口时平滑切换”的演进路径。
2. **个人信息保护与知情同意**
   - **风险**：从纯本机工具改为“校方服务器托管账密并经手查询”后，数据处理链路发生实质变化；若未充分告知就静默迁移，会引发合规与信任问题。
   - **对策**：上线前同步更新隐私说明，由学生主动确认后才启用后端模式；App 内提供清晰可见的“解绑并删除服务器加密账密”入口；旧本机密文在切换成功后立即清除。
3. **微信充值与图书馆预约的“高后果纠纷”**
   - **风险**：贴上官方牌子后，一旦出现“微信扣了钱但校园卡延迟 5 分钟没到账”“用户重复点充值”“图书馆抢座超时页面显示不准导致爽约扣分”，学生会直接投诉到学校。
   - **对策**：充值延续“拉起微信由本人付款 + 本地防重 + 回到 App 只读查单”，绝不把回跳当作付款成功，也不存支付链接或付款凭证；图书馆预约必须用户确认后单次提交，超时直接显示“结果未知，请核对官方记录”，绝不自动重试。
4. **“官方身份”带来的预期落差与舆情压力**
   - **风险**：民间工具时大家对小故障很包容；收编后哪怕是教务系统本身一天才同步一次、或者学校网络抽风，学生第一时间怪的也是 App。
   - **对策**：关键页面把**数据来源、学校更新时间、本次查询时间**写明白（例如提示“临时调课请以教务网为准”“到账以一卡通官方记录为准”），减少信息差引发的误解。

## 四、分发渠道、多端与系统适配问题

1. **普通学生装不上 APK（国产手机风险拦截）**
   - **风险**：以前走 GitHub Releases / gh-proxy 面向熟悉技术的同学没问题；全校推广后，华为、小米、OPPO、vivo 等系统安装非商店 APK 会频繁弹出“未备案/高风险应用”拦截，大量普通同学直接放弃安装。
   - **对策**：尽早规划学校主体的 **App ICP 备案**和正规应用商店上架；同时在校内官网提供 HTTPS 高速直链下载，摆脱 GitHub/gh-proxy 波动。
2. **应用内自更新与商店规则冲突**
   - **风险**：目前版本自带应用内检查更新与下载 APK 功能；一旦上架主流国产应用商店，商店通常禁止应用内自带 APK 下载安装器，否则审核会被拒。
   - **对策**：提前做好按分发渠道区分更新策略（官网直链版保留签名校验更新，应用商店版跳转商店更新）。
3. **未来做原生 iOS 的上架门槛**
   - **风险**：不要指望用苹果企业证书分发（极易掉签且违规）；正规上架 App Store 需要学校法人主体申请开发者账号（含 D-U-N-S 编码等材料，耗时较长），苹果审核还会核查学校官方授权函、隐私清单、微信支付场景及可用的审核演示账号。
   - **对策**：如果学校确定要做原生 iOS，尽早启动学校苹果开发者账号申请，不要等代码写完再卡在资质上。
4. **国产手机省电策略导致小组件和提醒延迟**
   - **风险**：全校推广后，普通学生不会手动关闭“电池优化”，很容易反馈“桌面课表没自动切下一节”“余额小组件半天不刷新”“待办提醒晚了”。
   - **对策**：不要为了强保活去申请高危后台权限（容易过不了安全评估和商店审核）；在设置和小组件说明里用人话写清楚受系统省电限制，点开即可立即刷新。

## 五、协作边界、权责归属与长期运营问题（最容易“收编即烂尾”）

1. **需求膨胀：小心变成臃肿的“校园大杂烩”**
   - **风险**：收编后，各个学院、学工、团委、后勤都可能来提需求——加开屏广告、塞问卷调查、强推活动弹窗、接各种低频打卡页，最后把轻量好用的工具做成一个大家讨厌的臃肿软件。
   - **对策**：提前和牵头单位定好产品原则：核心刚需服务优先、首页保持克制、不接强制开屏广告，新增功能必须经过统一评审与验收。
2. **客服与投诉黑洞**
   - **风险**：上万名学生用起来后，每天都会有人问“密码忘了怎么找回”“为什么我选不上课”“校园卡消磁了怎么办”——这些本质上是学校原有业务问题，但学生会全找 App 开发者。
   - **对策**：收编前必须定好**客服分流机制**（App 内放常见排查指引 + 校方指定反馈通道），把学校各业务系统本身的问题明确分流回原服务台，只把 App 自身故障转给开发团队。
3. **核心开发者毕业、寒暑假空窗与证书过期**
   - **风险**：高校学生项目被收编后最常见的结局：核心作者大四一毕业，后端代码没人接手、HTTPS 证书或密钥到期没人续、考试周/寒暑假出故障没人修，一年后项目荒废；或者反过来，开发者毕业了还要长期免费当售后。
   - **对策**：
     - 架构坚持简单主流，交接文档、部署回滚手册、自动告警和证书自动续期从一开始就配齐；
     - 谈收编时就明确**长期维护机制**（例如纳入学校技术社团/创新实验室梯队传帮带，或校方指派固定技术老师共管），同时说清核心开发者的参与期限、退出交接方式和署名/激励。
4. **开源协议、源码归属与署名权**
   - **风险**：项目包含上游开源项目版权、第三方依赖许可（如 Apache-2.0 等）以及学生团队长期原创代码。如果收编时没说清源码归属和许可义务，后续容易在开源合规、简历展示或二次开发上产生扯皮。
   - **对策**：在正式合作协议或纪要中写明：严格保留上游版权与开源许可证；明确后续代码归属与使用范围（继续开源还是转校内仓库）；保留开发团队在应用“关于”页与公开宣传中的规范署名。

## 六、下次和校方开会最值得顺手确认的 6 句话

1. **白名单与校外风险**：校内系统出口白名单由谁批？超星、微信这类校外接口如果被限流，咱们是不是先保留回退官方页？
2. **防锁号与高峰保护**：咱们后端按“密码错一次就停自动重试 + 高峰限流熔断”来做，教务/一卡通那边有没有具体的调用频率红线？
3. **包名与老用户**：正式收编后能不能继续沿用现在包名平滑升级，保住老用户的待办和日程？
4. **分发与备案**：App ICP 备案、校内下载页和后续应用商店/iOS 开发者账号，学校这边由哪个部门牵头办？
5. **客服分流**：推广后学生的密码找回、一卡通到账、教务排课咨询，咱们统一引流到哪个校方渠道，避免全砸到开发团队？
6. **长期维护与署名**：后续怎么安排梯队接班和校方共管，避免我们毕业后项目断档，同时把团队署名和开源合规也提前定好？
