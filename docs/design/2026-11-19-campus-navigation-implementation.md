# UPC Pocket 校园导航核心开发计划

**日期**　2026-11-19

**目标**　从校内当前位置选一个目的地，比较步行或骑行路线，进入地图内的实时导航。用户能看到下一步文字指引，走偏后能继续沿新路线前进。

**状态**　本页保留最初计划及 SDK 验证方案。开发采用 OSM 底图、离线步骑算路和 Android 前台定位，课表地点入口一并接入。现场通行与定位表现仍待验收。 [当前架构决定](../adr/007-offline-campus-navigation.md) · [校园地图导航共创提案](2026-11-19-campus-map-navigation-plan.md)

## 1. 这轮交付什么

- 唐岛湾、古镇口各自支持校内导航，地图内可切换校区。首个入口为「服务 → 校园地图」，可沿用服务目录已有的首页固定能力。
- 地图显示当前位置与定位精度。目的地可点地图标记或搜楼名、简称。地点清单先覆盖教学楼、宿舍、食堂和图书馆，终点尽量落到可通行的楼门。
- 普通步行、普通自行车分别算路。每次最多展示 3 条真实可用的路线，标出预计时间和距离，默认最快。
- 在前台地图内沿选中路线导航，更新下一步文字、剩余距离和时间，支持偏航重算、到达和手动结束。

这份计划把课表地点直达和校园路况标注列在核心闭环之后。课表入口保留在整体共创需求中，等核心导航通过验收再接。跨校区、室内楼层、语音和锁屏后台导航留在后续讨论范围。

## 2. 页面流程

| 页面状态 | 用户看到什么 | 操作后的结果 |
| --- | --- | --- |
| 地图浏览 | 校区切换、地点标记、搜索框、定位按钮 | 点标记或搜索结果进入地点卡。地图拖动后可用「回到当前位置」。 |
| 地点卡 | 楼名、校区、类别、已核实的入口 | 点「去这里」进入路线页。重名时先选校区和楼栋。 |
| 路线预览 | 起终点、步行／骑行切换、地图路线、预计时间及距离 | 默认选最快。点其他候选同步切换高亮线和路线卡。点「开始导航」走选中的线。 |
| 导航中 | 当前位置、下一步文字、剩余时间和距离、结束按钮 | 偏航时提示正在重算。成功后换成新线。到达入口时提示结束。 |
| 需要处理 | 当前状态和一个可操作的入口 | 拒绝定位可改手动起点预览。定位不稳时提示等待或重试。无有效路线时可换起点、终点或出行方式。 |

起点默认取可信的设备定位。手动起点用于预览。开始实时导航时如果当前位置明显偏离预览起点，先以当前位置重新规划，再让用户确认。当前人在校区之外时，允许浏览或手选校内起点，实时导航在进入对应校区且有可靠定位后开启。

## 3. 先验证地图 SDK

**用百度步骑行 SDK 做第一轮原型，高德作为对照。** 百度的官方类参考有步骑行规划列表和按原路线索引进入导航的接口。高德独立算路指南公开了骑行、步行与路线组选线接口。两家的能力都以实际选择的 SDK、账号权限和两校区走测为准。 [百度步行导航助手](https://mapopen-pub-androidsdk.cdn.bcebos.com/map/9_0_0/com/baidu/mapapi/walknavi/WalkNavigateHelper.html) · [百度骑行导航助手](https://mapopen-pub-androidsdk.cdn.bcebos.com/map/9_0_0/com/baidu/mapapi/bikenavi/BikeNavigateHelper.html) · [高德独立算路](https://lbs.amap.com/api/android-navi-sdk/guide/route-plan/independentcalculateroute)

- [ ] **校内覆盖**　在每个校区各实测至少两组步行和两组骑行路线，包含一组去教学楼实际入口、一组能观察到步骑行路径差异的路线。核查门的位置、校内小路、可通行性和是否绕出校区。
- [ ] **选线一致**　步行和骑行分别找一组确实有备选的起终点，选非默认路线后开始导航，核对导航折线或当前路线标识与预览一致。路线列表排序后仍传 SDK 原始路线标识或索引，不使用列表下标替代。
- [ ] **数据与引导**　拿同一条路线核对距离和耗时单位，验证普通转向、剩余指标、到达和一次偏航重算。百度骑行指南注明部分定制引导信息需高级权限，先确认项目账号可用的回调。若定制回调受限，验证能否在 App 内嵌入官方导航视图显示文字。 [百度骑行指南](https://lbsyun.baidu.com/docs/android?title=androidsdk/guide/navigation/bikenavi) · [百度引导授权类型](https://mapopen-pub-androidsdk.cdn.bcebos.com/map/9_0_0/com/baidu/mapapi/common/auth/BWAuthLicenseType.html)
- [ ] **集成与许可**　用准备采用的 AAR 核对原生 ABI、APK 增量、合并 Manifest、发布包名与签名对应的 Key、配额和公开使用许可。沿用 minSdk 31、compileSdk 36 和 targetSdk 36，供应商缺失的 ABI 单独记录给维护者决策。 [构建指南](../BUILD.md)
- [ ] **选型结论**　达成同路线、前台指引与两校区覆盖后固定一家 SDK 和版本。无法同线启动时先换官方接入方式或对照另一家。原型如果只跑通路线预览，记录为预览阶段，完整导航后续再验收。

技术验证用公开地点和真实走测。正式接入前核对各地图服务的使用许可和隐私条款。 [百度 SDK 须知](https://lbsyun.baidu.com/docs/android?title=androidsdk/index) · [高德导航 SDK 须知](https://lbs.amap.com/api/android-navi-sdk/summary/)

## 4. 按顺序做五个小交付

### 第一步　选型原型与公开地点样本

- [ ] 给两校区各整理一份路线验证表，字段含起点、目的地、楼门、方式、候选条数、是否同线开始及结果。使用公共地点和核实过的入口，截图或记录个人信息前先脱敏。
- [ ] 按第 3 节完成两家 SDK 的最小验证，记录合格供应商、所需权限、已知覆盖缺口和包体影响。原型单独验证，过关后再接进主应用。

阶段交付是可复核的选型记录和校园路线样本。估时 2–3 个开发工作日，平台审核与现场安排另计。

### 第二步　接入口、地图和定位

- [ ] 新建 `feature:campus-navigation` 内置插件。更新 `settings.gradle.kts` 和 `app/build.gradle.kts`，由 `AppGraph.kt` 注册插件，选定的 SDK 版本固定在 `gradle/libs.versions.toml`。通过现有服务目录贡献「校园地图」二级页。
- [ ] 在页面内用 `AndroidView` 复用 SDK 地图视图，提供两校区切换和当前定位标记。由宿主把常用校区偏好转换成导航模块的校区值。仅在使用地图且取得所需同意后初始化 SDK。
- [ ] 加入项目维护的公开地点清单。记录地点编号、校区、楼名、别名、类别、可走入口、坐标系、来源和核实时间。校内点选和楼名搜索使用同一清单。
- [ ] 添加用户主动定位时的权限流程。精确与粗略定位由系统选择。粗略定位下显示精度范围并支持手选起点。权限拒绝、定位关闭、定位过期和校区不符分别提示。

阶段交付是在无学校账号的情况下可进入地图、切校区、定位和选点。估时 2–3 天。 [架构与装配](../../ARCHITECTURE.md#启动扩展与导航) · [插件契约](../../API.md#插件能力与-ui) · [Compose 与原生视图](https://developer.android.com/develop/ui/compose/migrate/interoperability-apis/views-in-compose) · [Android 位置权限](https://developer.android.com/develop/sensors-and-location/location/permissions/runtime)

### 第三步　完成步骑行候选与选路

- [ ] 在导航模块用一个供应商适配层返回候选，统一为路线标识、方式、折线、距离和预计时间。适配层持有 SDK 原始路线标识或索引和本次算路代次，界面只传选中的业务路线标识。
- [ ] 过滤无效候选、重复折线和越出校区的路线。校区边界、入口位置及通行性用核实过的数据和走测判断。未核实的校园小路标为待核实，避免按照直线距离拼出路线。
- [ ] 按预计时间升序排列，同时间时按距离排序，最多取 3 条。有一条就显示一条。切换方式、修改终点或起点时生成新请求，丢弃旧回调。
- [ ] 在路线卡和地图之间同步选中状态，用选中的同批 SDK 路线开始导航。算路失败、无校内候选、服务超时或配额限制分别展示。

阶段交付是可实际比较和选中两种方式的路线，选第二条时进入第二条的引导。估时 2–3 天。

### 第四步　完成前台导航和偏航重算

- [ ] 会话状态覆盖「待开始、导航中、定位暂不可用、重算中、已到达、已结束」，只保留一个活动会话。下一步动作与剩余距离、时间来自当前导航回调。
- [ ] 使用 SDK 的偏航事件触发重算，配合定位精度和连续可信数据过滤跳点。避免 SDK 自动重算与 App 同时发起重复请求。新线成功后替换旧线，失败时让用户重试，同时明确当前指引状态。
- [ ] 锁屏、切后台、结束导航或撤销权限时，停止页面定位订阅并调用 SDK 的对应暂停或停止接口，验收时确认供应商定位也已停止。返回前台先取新的可信定位，再按实际情况恢复或重新规划。迟到的定位与引导回调按会话代次丢弃。
- [ ] 地图视图只创建一次并随页面释放。定位回调更新标记和指引，地图相机只在跟随模式下按需更新。控制覆盖物数量，保持路线和文字对比清晰。

阶段交付是在两校区分别走完步行与骑行，以及一次人为走偏后的重算。估时 3–4 天。 [百度步行引导回调](https://mapopen-pub-androidsdk.cdn.bcebos.com/map/9_0_0/com/baidu/mapapi/walknavi/adapter/IWRouteGuidanceListener.html) · [百度骑行引导回调](https://mapopen-pub-androidsdk.cdn.bcebos.com/map/9_0_0/com/baidu/mapapi/bikenavi/adapter/IBRouteGuidanceListener.html)

### 第五步　验收与小范围试用

- [ ] 用定向单元测试覆盖地点别名、同名校区、候选排序及供应商路线标识映射、过期算路回调和偏航防抖。宿主检查地图入口、首页固定行为和插件缺失时的降级。
- [ ] 用模拟器验证页面与权限常规流程，再用实体安卓手机实测两校区。覆盖只返回一条、能选非默认路线、弱定位、重算与到达。观察较低性能真机的地图操作、定位更新、包体和耗电。
- [ ] 更新 M5 入口说明、隐私说明和受影响的架构／接口文档。按 [构建指南](../BUILD.md) 与 [贡献规范](../../CONTRIBUTING.md) 运行模块边界检查、导航模块定向单测和必要的签名安装冒烟。
- [ ] 记录每校区的入口准确性、失败场景、设备和修复状态。通过后以可单独关闭的入口交付小范围试用，确保其他校园功能照常可用。

阶段交付是两校区验收记录和可试用的签名构建。估时 1–2 天。

**核心开发估算为 10–15 个工作日**，以一位熟悉现有项目的安卓开发者为基础。两校区实地配合、SDK 资格审批和楼门数据核实可能影响日程。核心验收通过后再约定课表入口的实现时间。

## 5. 全程约束

- 业务路线请求只传必要的起终点与出行方式。个人轨迹、搜索词和课程内容留在必要的页面或会话内存。第三方 SDK 的设备及网络数据处理按实际版本的隐私说明披露。应用诊断使用固定状态和有界计数。 [项目隐私](../PRIVACY.md) · [百度开放平台隐私资料](https://lbsyun.baidu.com/docs/pcsa?title=compliance%2Fopenprivacy)
- 地图供应商底图与团队公共地点清单分开管理。坐标系转换放在 SDK 适配边界。校区通行管制仅使用经核实的数据。现场走测负责确认路线实际能走，SDK 文档和模拟器结果分别记录。
- 地图能力封装在导航 feature 中，其他 feature 通过宿主已注册入口调用。常用校区由宿主注入，地图 SDK 不作为全应用启动依赖。 [ADR 001 插件边界](../adr/001-module-and-plugin-boundaries.md) · [入口映射](../m5/README.md)

## 6. 2026-11-20 现有覆盖验收

开发版沿用道路底图，随 App 分发唐岛湾 92 个和古镇口 29 个可搜索地点。路线由本机道路图计算。验证包括模块边界检查、导航模块 6 项单测和 Debug 整包构建。导航单测覆盖同线路引导、步骑方向限制、校区范围、定位有效期、起步转弯及折返路段误匹配。

使用 App 随附的实际路网和同一算路器完成以下预览。距离与候选数属于数据和算法验收。

| 校区 | 样例 | 步行首选 | 骑行首选 | 步行／骑行候选数 |
| --- | --- | ---: | ---: | ---: |
| 唐岛湾 | 南门 → 图书馆 | 649 米 | 698 米 | 3／3 |
| 唐岛湾 | 17 号学生公寓 → 工科楼 E 座 | 814 米 | 920 米 | 3／3 |
| 古镇口东区 | 综合教学楼 → 文体中心 | 484 米 | 484 米 | 3／3 |
| 古镇口东区 | 观海苑餐厅 → 校医院 | 324 米 | 324 米 | 2／2 |

古镇口西区「珠山餐厅 → 学 8」在两种方式下均正确返回无可用路线。用户确认先验收现有覆盖。西区校内道路、建筑实际入口和实体手机走测继续待核。

宿主入口与课表地点交接的 24 项定向测试通过。模拟器以独立包名安装 Debug 测试版，已从服务页打开地图、搜索两栋公寓，以手动起点比较步行和骑行路线。合并清单的定位权限为前台粗略与精确定位。实现核对了[仓库架构](../../ARCHITECTURE.md)、[插件契约](../../API.md)、[入口映射](../m5/README.md)和[隐私说明](../PRIVACY.md)。

模拟定位在 1 号学生公寓楼栋中心时，地图引导前往绿色道路起点。将模拟位置移到道路起点后，从所选骑行候选第 2 条启动导航，界面显示剩余 640 米、约 3 分钟。结束导航后回到路线预览。以上为模拟器验证，偏航重算和到达仍需实地核对。

## 7. 定位与课表地点修复

获准使用精确位置后，地图使用 Android 的高精度请求。已有较准结果时短暂抵抗精度骤降，结果过期后更新状态。地图显示系统估计的定位精度。系统只授予大致位置时，可在地图上选「开启精确定位」。

课表里的「南教110」匹配南教楼。「微」加房号按已确认的课表简称匹配基础实验楼 D 区。D 区使用独立的建筑点位。地点后跟房间号时优先匹配更具体的楼栋名称，房号后的括号说明可保留原样传入。同等匹配或校区冲突时保留地点待选状态。 [D 区建筑轮廓](https://www.openstreetmap.org/way/924350836)

导航模块 10 项单测和独立测试版 Debug 构建已通过。用随包数据确认了两个房间号及全角数字的匹配。模拟器注入 5 米精度的测试位置后，地图显示「定位精度约 5 米」。手机现场定位精度待核。
