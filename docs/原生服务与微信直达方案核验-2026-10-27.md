## 结论

用户要的方向是：原生余额、原生空闲教室、原生座位交互、批量课表导入，以及点击后从 App 进入微信目标服务。复制链接只是兜底，不能算直达完成。此前把“没有已验证通用方案”说成“不能直接跳转”，结论过强。

## 微信直达：两条路线

### OpenWebview 真机实验

腾讯发布的 Maven 构件 `com.tencent.mm.opensdk:wechat-sdk-android:6.8.40` 中存在 OpenWebview.Req，sendReq 对该类型仍有实际分发，不能仅称为一个历史空类。其存在证明可以研究，并不证明任意第三方应用都已取得微信客户端的使用资格。

实验必须使用真实注册的移动应用身份和实际包名/签名，经 SDK 调用，不手工调用内部 Provider、不借用其他应用 AppID、不固定私有 Activity。测试分别记录：SDK 发送结果、微信是否进入目标页、学校 OAuth/余额页是否成功。仅启动微信或 sendReq 返回成功，都不能算完成。

本轮未找到当前官方公开文档明确保障普通第三方 App 可通过该请求打开任意 H5，也未在装有微信的手机上验证。SDK 中发现实现不能代替真机证据。

构件：[Maven AAR](https://repo.maven.apache.org/maven2/com/tencent/mm/opensdk/wechat-sdk-android/6.8.40/wechat-sdk-android-6.8.40.aar)。SHA256：C3C3215F2BC7F6AAD0454541F9BDD91878CDB15B64D35E194A6C9240000C5D48。

### 小程序官方直达

优先使用目标小程序所属方提供的 URL Link；Android 默认会经过微信官方 H5 中间页，可能需要用户确认，不需要复制到聊天窗口。另一种是 UPC Pocket 正式接入 SDK 后通过原始 ID/页面路径拉起小程序。这两种不能把目前的 HTTP H5 地址直接当作小程序标识。

官方当前文档说明：URL Link 针对非个人主体小程序、只能生成已发布的小程序链接。链接生成/有效性由目标方控制，不应把别处复制的临时链接写死给所有用户。

已确认学校有“i石大·电子身份卡”和“石大e站通”小程序，但没有证据证明它们就是电费/校园卡余额服务，不得以名称相近代替目标核实。当前学校公开资料确认的校园卡入口是学校微信企业号中的“校园卡服务大厅”。

若学校当前只有 H5，可合作由机构小程序的 web-view 承载，再提供官方直达链接；需要学校配置 HTTPS 业务域名。现有两个 HTTP 地址（校园卡还使用 20081 端口）不能直接假定符合要求。自建小程序不是自动取得学校登录或域名权限的捷径。

参考：[URL Link](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/url-link.html)、[URL Scheme](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/url-scheme.html)、[App 拉起小程序示例](https://qian.tencent.com/developers/company/openwxminiprogram/)、[web-view](https://developers.weixin.qq.com/miniprogram/dev/component/web-view.html)。

## 原生余额与座位：登录页和功能页分开

可以保留官方网页作为必要的登录步骤，登录之后用原生页面显示余额或座位，而非把整个产品变成浏览器。能否通过浏览器回调、设备内认证会话或官方 API 完成承接，需要按各系统真实行为验证。系统浏览器、App WebView、微信三者不自动共享登录态；CAS 成功也不意味着自动拥有所有系统的会话。

会话仅保留设备，凭据和业务数据不写源码、测试样本或日志；退出时清除。若后续需要持久会话，应明确存储和备份策略，不能继续使用当前“App 不保存 Cookie/Token”的旧能力说明。

唐岛湾给定地址匿名访问会跳转微信 OAuth；校园卡裸链接 HTTP 200 的正文是无效 token。前者说明有真实认证链，后者说明裸地址不是完整查询流程；均不能靠改 User-Agent 解决。

学校 2026-10-21 的[《数据科常用问题汇总》](https://appnic.upc.edu.cn/2026/1021/c25387a284780/page.htm)给出[数字石大](https://i.upc.edu.cn/)的统一认证入口，可在本人正常登录后找同业务的普通网页版本。但这不等于本轮已验证电费和校园卡支持 CAS。该文第 29 项还列出学校正式数据接口对接途径，可作为长期稳定集成路线；本轮没有代用户提交申请或联系他人。

[校园卡使用指南](https://app.upc.edu.cn/wap/material?id=11551)说明支持脱机消费与待圈存款项，余额模型需区分金额含义并显示更新时间，不能把所有金额都标为实时可用余额。

图书馆[普通座位页](https://libspace.upc.edu.cn/libseat/)的[公开配置](https://libspace.upc.edu.cn/libseat/static/baseUrl.js)启用 CAS。公开前端存在会话和请求签名，原生实现不能只照搬几个 URL；应按正常认证与业务交互适配，界面包含预约结果、我的预约与取消，避免把请求已发送当作预约成功。

## 课表：登录后提取，再交本地解析

推荐流程：本人在教务系统正常登录 → 打开本人课表 → 主动点击导出工具 → 仅提取已显示的课程区域 → 生成 CSV/JSON 文件或使用 Android 分享 → App 内预览、校验、去重和事务导入。

电脑端可以用只在点击时获得 activeTab 权限的扩展；手机端可以提供针对实际浏览器验证的用户脚本，或把必要的登录与课表导入页放入专用导入流程，导完即回原生课表。普通分享网页 URL 不会自动传回页面课程内容。

当前公开组件有 `.weekschedule-page` 及课程、地点、教师、周次、时间等结构，但未取得真实登录 DOM，不能现称脚本已经适配。只渲染当前周时，工具必须标明当前周，不能推断整学期。原有 1–10 节上限应与真实 UPC CSV 一起完善，不能静默丢弃 11–13 节。

参考：[Chrome activeTab](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab)、[Android 文件选择](https://developer.android.com/training/data-storage/shared/documents-files)、[Android 接收分享](https://developer.android.com/develop/ui/compose/sharing/receive)。

## 建议推进顺序

1. 核验真实教务导出格式，完善一学期导入与真实节次；增加只读页面导出工具。
2. 图书馆按正常 CAS 登录验证数据连接，再实现原生选座与预约状态。
3. 微信以正式 AppID 做 OpenWebview 兼容性实验，同时确认学校目标小程序/企业号入口；只有真机目标页成功才标为直达。
4. 电费/校园卡分别完成正常认证与只读数据链验证后做原生余额，不先造一个虚假余额页。

本轮只读取公开资料、脚本和未登录入口；没有登录用户账号、读取微信会话、预约、充值、提取个人 Token 或访问个人余额。
