# UPC Pocket 应用内更新方案 v0.1

日期：2026-11-06。讨论与研究稿，未实施、未部署、不代表已发布能力。

## 目标与结论

在 2.0.1 中增加应用内检查、下载、校验与系统确认安装。保持界面简洁，不引入第三方更新 SDK、不自建业务服务器、不增加首页卡片。GitHub Release 仍为发布源，公网加速服务仅负责传输。

高校镜像同步的是指定项目，不能作为任意 GitHub 仓库的通用下载代理。当前不将清华、中科大、北外或南京大学列为 UPCPocket 可用线路；若以后正式收录并验证完整产物，再加入。

### 本机实测

样本为已公开发布的 `v2.0/UPC-Pocket-2.0.apk`，4,625,769 bytes。测试进程关闭环境代理，启用正常 TLS 校验，每个来源各请求一次；没有登录、令牌或校园请求，不修改全局网络设置。

| 线路 | 本次结果 | 耗时 |
| --- | --- | ---: |
| gh-proxy.org | HTTP 200、完整 APK，SHA-256 与官方已知值一致 | 2.64s |
| ghproxy.net | HTTP 200、完整 APK，SHA-256 与官方已知值一致 | 14.35s |
| GitHub 官方 | 建连超时，无文件 | 6.07s |
| ghfast.top | 读取超时，无文件 | 6.63s |

官方样本 SHA-256：`00edd4e78ed2e0fc3436a21960d6a66205559946848e0cde514ada08dfc47eef`。这不是跨地区测速、长期稳定性评估或服务承诺；不能把本机速度当作用户手机速度。

## 用户交互

入口：现有设置 → 关于 → 检查更新，右侧显示当前版本。复用现有页面，不新建“更新中心”顶级入口。

- 前台启动每天最多检查一次，可在关于页关闭自动检查；只检查元数据，不自动下载、不后台周期联网。发现新版给轻量提示，不打断账号登录或预约确认。
- 手动检查始终可用，正在检查时合并重复点击。
- 弹窗只显示新版本、包体大小、3–5 条更新内容、“更新”和“稍后”。拒绝后同一版本不在每次启动重复弹出；手动检查仍能更新。
- 下载时显示进度、“自动线路”、“切换线路”和“取消”。无需用户填写镜像 URL。
- 下载完成、完整校验通过后显示“安装”。首次安装授权按系统流程处理，返回后继续，不重复下载。
- 系统负责最终安装确认。不得静默安装、强制更新、卸载旧包或清除数据。
- 错误用短句：检查失败、线路不可用、下载中断、校验失败、安装未完成。不把请求失败显示为“已是最新”。

## 更新清单与信任

不依赖仅可直连的 GitHub API。每次发布在同一 Release 上传：

- `UPC-Pocket-<version>.apk`
- `update.json`
- `update.sig`
- 人工比对用 `SHA256SUMS.txt`

`update.json` 建议包含：schemaVersion、packageName、versionName、versionCode、minSdk、tag、assetName、sizeBytes、sha256、publishedAt、纯文本 notes。版本以整数 versionCode 比较，不以版本字符串或发布时间猜测。

清单采用独立更新密钥签名：优先使用 Android 现有平台密码能力支持的 ECDSA P-256 / SHA256withECDSA，公钥随应用发布，私钥留开发端仓库外。`update.sig` 是对 `update.json` 原始 UTF-8 字节的签名，避免重新序列化后校验；固定编码、严格长度和算法，禁止远程指定任意算法。该密钥不取代 APK 签名，也不要求更换 APK 证书。

下载清单和签名必须来自同一候选源/同一发布快照，签名有效才解析并使用内容。候选源正在同步、清单与签名不匹配时切源，不安装。公网镜像的 SHA-256 文本不能单独充当真实性依据；先验签清单，再用其中哈希验证 APK。

只接受本项目包名、正整数更高版本、支持的 minSdk、固定仓库、合法 tag/文件名与有界大小。基于固定仓库和文件名生成地址，不执行更新说明 HTML/脚本，不接受清单给出的任意主机。优先保留最高已验证 versionCode，禁止镜像重放降低已经观察到的版本；但未见过新版的客户端仍可能遇到镜像同步延迟，不能承诺实时获知最新。

不要把“加速线路配置”做成远程任意域放行。第一版内置少量固定域，未来切换传输域仍校验签名。公开更新请求不带学校 Cookie、账号、设备唯一标识或开发者 GitHub token。

## 线路策略

### 检查版本

官方地址为本项目 `releases/latest/download/update.json` 与 `update.sig`；第一版推荐顺序：最近成功的候选源 → 主加速 → 备用加速 → GitHub 官方，去重后每个来源最多尝试一次。首次优先主加速，防止每次都先等待已知不可达的官方地址。

建议每源清单/签名合计预算 6–8 秒，整次检查最长约 20–25 秒；清单上限 64 KiB、签名上限 1 KiB。使用本机缓存与条件请求降低频率，但缓存不能伪造本次联网成功。达到预算即短提示，允许用户手动重试或打开发布页。候选域需在实施前复查：`gh-proxy.org`、`ghproxy.net`、GitHub 官方。

不要在启动时向每条线路下载 APK 测速，不并行下载整包；最近成功源仅是性能偏好，不提升信任级别。GitHub API 可用作补充核对，不作为独立单点依赖或替代清单签名。

### 下载 APK

用已验证清单内的精确 tag/assetName 下载，禁止使用可变化的 latest APK 链接。所有线路必须对应同一大小和 SHA-256，不能跨版本切换。

用户确认后单任务下载至私有专用目录，先写 `.part`，有明确进度、取消和超时。主源失败后换下一源，最后保留官方与浏览器兜底。第一版包约 5 MiB，跨源从头下载即可；不实现容易拼错文件的跨源断点合并。以后如加断点需校验 ETag/Range/长度，完成后仍验证整个文件。

只接受 HTTPS、受控来源和经核对的 GitHub CDN 重定向链，限制跳转次数，不向下一域带 Authorization/Cookie，不忽略证书错误。校验长度/下载上限和 SHA-256，然后检查 APK 包名、内部 versionCode、minSdk 与当前签名兼容性；系统安装器再做最终 APK 签名检查。不匹配删除临时文件，不建议用户卸载绕过。

应用内下载无需广泛存储权限；FileProvider 只暴露更新包专用子目录，临时只读授权给系统安装器，不能沿用开放整个缓存的配置。安装来源授权只在用户点击安装时请求。按现有组件/任务架构选择前台可恢复的有限下载任务，不为约 5 MiB 文件引入保活服务或大 SDK。

## 发布与版本

该功能可以并入仍未正式发布的 2.0.1。建议最终 versionName 保持 `2.0.1`，versionCode 从复测包的 `21` 提升至 `22`，避免同名复测版本检测不出内部升级。

2.0 与目前 r3 没有更新器，用户仍需手动安装一次含更新器的 2.0.1；不能让旧包凭空获得应用内更新能力。

发布脚本应先构建/验收 APK，确定字节数/哈希/签名与 versionCode，生成并签署清单，上传 APK、清单、签名后再公开 Release。发布资产不在公开后原地替换，重发修复必须提高 versionCode。私钥、GitHub token 和 R8 mapping 均不作为附件。

## 测试与工作量

首版难度中等，工作集中在安全下载、授权返回和故障恢复，不在弹窗。分为：

1. 清单模型/签名校验、版本比较、限定源策略及发布脚本。
2. 关于页检查入口、轻量提示、有限下载/进度/取消、系统安装。
3. 镜像失败回退、元数据不同步/重放、网络恢复与 Release 真机验收。

必要测试：两加速源/官方失败切换、错误 HTML 下载、坏签名/坏哈希、包名/证书不匹配、旧版本/同版本、清单与签名不同步、断网/取消/进程重建、授权拒绝/返回、安装取消、旧缓存和下载文件清理。安装必须保留用户数据，不用 adb install 成功冒充系统更新流程成功；API 36 模拟器和至少一台用户手机完成一次高 versionCode 覆盖更新。

更新诊断只记固定阶段/线路 ID/结果/耗时/HTTP 状态，不导出完整重定向 URL 或文件路径。不读取校园接口，不影响已经通过用户复测的课表修复。
